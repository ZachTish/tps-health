## Native Daily Note dashboard

In **Native Markdown records** mode, Health stores nutrition on the `food-entry` record and does not copy a summary into the Daily Note. Add this fenced block to a Daily Note template to render the day from the incremental native-record index:

````markdown
```tps-health-daily
```
````

The containing file must resolve through Core Daily Notes. The dashboard uses that note's date, not today's wall-clock date. It renders configured food metrics only; activity minutes stay in the Activity record/Base rather than being mixed into nutrition totals. A companion core Base can show the actual records with `note.kind == "food-entry"` and `date(note.date) == date(this.file.name)`. The fenced block contains no stored totals, and Source mode therefore remains ordinary literal Markdown.

## Daily Note Lines

TPS Health does not maintain a second Daily Note folder or filename-format preference. It reads Obsidian's Core **Daily notes** settings whenever it resolves a date, with the saved `.obsidian/daily-notes.json` values available during startup before the live core-plugin options are ready. Live Core values win field-by-field—including an intentional vault-root folder—and `YYYY-MM-DD` at the vault root is the safe fallback when Core has no saved value. Date formats containing `/` create the required nested folders. The **Daily logging** settings page links directly to Core Daily Notes instead of duplicating those controls. Legacy `dailyNoteFormat` and `dailyNoteFolder` values are removed from Health's settings on upgrade and never override Core.

Food logs are appended to the selected day's daily note body by default. The optional food heading setting can still route entries into a section, and the older single-file food log remains supported for legacy readback and tests, but daily notes are the active storage target for normal logging and Home-launched logging:

```md
- 1 serving - [[Health/Foods/Greek yogurt|Greek yogurt]] <!-- [type:: foodLog] [food:: Greek yogurt] [qty:: 1] [unit:: serving] [servings:: 1] [foodServingAmount:: 1] [foodServingUnit:: serving] [nutritionSnapshot:: true] [cal:: 120] [protein:: 15] [carbs:: 8] [fat:: 2] [foodPath:: Health/Foods/Greek yogurt.md] [foodId:: food-...] [createdDate:: 2026-06-01T15:00:00.000Z] -->
```

Every workout has one ordinary Daily Note task linking to its real level-2 session heading. A saved workout template inserts its exercise/set placeholders in that bounded section; a blank workout starts with no exercise rows. In Live Preview both session-boundary comments and their line boundaries are atomic replacement ranges: cursor movement and ordinary deletion commands skip them, the rendered lock identifies the session marker as protected, and the end boundary stays invisible. Active legacy workouts without an end marker or task are bounded and repaired without consuming unrelated tasks or prose. ## Food And Recipe Notes

Reusable foods, recipes, and meals are Markdown files recognized according to **Food note identification**. Frontmatter-capable modes show the identity property key plus separate food, recipe, and meal values. The defaults write `kind` with the appropriate value; this example uses a custom `healthEntity` key in the combined mode:

```yaml
---
healthEntity: pantry-item
name: "Greek yogurt"
tags:
  - tps/food
aliases:
  - "Costco yogurt"
  - "breakfast yogurt"
servingAmount: 1
servingUnit: serving
calories: 120
proteinG: 15
carbsG: 8
fatG: 2
---
```

Recipes and meals store their linked ingredient records in a YAML list while leaving headings, directions, and notes in the Markdown body:

```yaml
ingredients:
  - "1 egg - [[Health/Foods/Egg|Egg]]"
  - "28 g - [[Health/Foods/Mozzarella|Mozzarella]]"
```

Recipe frontmatter also stores `recipeServings` for the full ingredient list and saves per-serving macro totals so logging `1 serving` uses the correct fraction of the full recipe. Meals live in the recipes folder, use the same list property, share the configured recipe tag, and are fixed to `recipeServings: 1` with `servingUnit: meal`; that canonical serving unit keeps a tag-only or folder-only meal distinguishable from a multi-serving recipe without requiring frontmatter identity. Existing body-based ingredient rows remain readable and are migrated into `ingredients` when TPS Health next updates that recipe or meal. Packaged-food label text uses the scalar `ingredientStatement` property instead, avoiding a vault-wide Obsidian property-type conflict. The selected identification mode controls generated identity fields: **Tags only** writes only the normalized configured tag, **Frontmatter only** writes only the configured property key/value, **Folders only** relies on the configured folders and writes neither, and **Frontmatter, folder, or tag** writes both. The default frontmatter mapping is `kind: food`, `kind: recipe`, and `kind: meal`, but all four fields are editable beneath the mode selector. Updates remove TPS-owned identity fields excluded by the selected mode while preserving unrelated tags and metadata. New notes do not repeat an identifier as a standalone body line. Existing configured metadata, legacy `kind`/`tpsType`, folder, and legacy body-tag signals remain readable, so no vault-wide rewrite is required. Daily and single-file food-log notes are intentionally not given a reusable-food identity because each note contains many log instances; their per-line `[type:: foodLog]` fields remain in the body.

TPS-created recipe and meal notes normalize plain ingredient names into linked food-note list values when an exact saved food match exists. Creating a meal from the food tray snapshots the selected ingredients, replaces only those unchanged captured entries with the saved meal after creation succeeds, and keeps later or edited tray entries. Cancelling or failing the follow-up log leaves the saved meal queued; a successful log consumes that queued meal and clears the owned pending draft when nothing else remains. Draft compare-and-swap guards prevent an older logger from overwriting or clearing a newer tray. Obsidian's Properties view can remove or replace individual list values directly, while `TPS Health: Edit current food/recipe` opens the richer editor with calculated macros plus Replace, Remove, and Add controls. TPS Health validates the exact current source record and serializes its own mutations per recipe before refreshing frontmatter nutrition. Replace preserves the prior amount when supported and shows a fallback before saving when it is not; removing the final ingredient writes zero totals. The full recipe/meal editor preserves body headings and instructions plus custom wikilink labels. `+ Ingredient` searches foods, saves provider items as local food notes when needed, writes a linked metric list value, and refreshes recipe nutrition. Food macros are always computed from the linked food note and selected amount/unit without adding per-ingredient macro fields. Unresolved plain ingredients show that no linked food note was found. Legacy body ingredient cards remain supported until those notes are updated and migrated. Food, recipe, and meal notes are returned by the food logger search.

Contract invariant: a meal is the recipe composition model fixed to one serving, not a separate multi-serving structure. Canonical meal values are `recipeServings: 1`, `servingAmount: 1`, and `servingUnit: meal`, plus the configured meal identifier only when the selected identification mode writes frontmatter identity; its full ingredient total is its single-serving nutrition. Conflicting meal yield, metric-serving, or serving-unit fields are ignored when a meal is read and normalized whenever it is written. A recipe uses `servingUnit: serving` and may represent more than one serving.

Editing an existing food, recipe, or meal always asks how existing links should behave. `Update linked instances` modifies the current entity note so future searches, selections, and recipe resolution use the new source values; already-written food-log nutrition remains frozen in its line snapshot. Existing recipe ingredients keep their source path and continue to resolve the updated reusable food. `Create new version` writes a new unique entity path, returns that new entity to the active tray/editor callback, and leaves every historical link on the old path untouched. Cancel performs no write. Exact future barcode/name resolution prefers the newest matching entity so a newly versioned food becomes the default without rewriting history.

Editing a logged meal opens its full single-serving composition in the food editor. Each ingredient row shows quantity, unit, linked food, calculated calories/macros, and Replace/Remove actions; `+ Add ingredient` searches saved/provider foods and chooses a supported amount/unit. Changes stay local to the modal until Save, and invalid or empty ingredient amounts block submission instead of silently restoring an older value. Save then reuses or creates each linked food note and applies the same `Update linked instances` versus `Create new version` decision as other source-note changes. Linked updates preserve non-ingredient body content and synchronize an active editor with the committed frontmatter/body; Create new version preserves that structure at the new path. Cancel leaves the meal and provider candidates untouched. A logged meal instance continues to link to its existing source unless the caller explicitly adopts a newly versioned meal.

## Food Search And Creation

Saved food and recipe notes are indexed once per valid catalog generation instead of rescanning every Markdown file for every keystroke or barcode. Relevant vault create/modify/delete/rename and metadata changes invalidate the catalog, while settings that change food or daily-log ownership invalidate the corresponding catalog or usage index. The complete usage-history scan is also reused for local ranking and the Saved recent/frequent groups. These indexes are in-memory accelerators only; the Markdown notes remain canonical.

`Log food` opens as one tray-first logger with five short modes: **Scan**, **Search**, **Saved**, **Describe**, and **Quick add**. `Scan food barcode` opens this same logger directly on Scan rather than creating a separate review/logging path. Scan starts the camera immediately, returns a matched food to the existing selected-food tray, and retains manual UPC/EAN and image fallbacks. Saved shows recent/frequent foods plus saved local food and recipe notes without a provider request; its “My foods” list is built only from actual saved notes, so built-in suggestions cannot displace the user's catalog. Tapping a result adds it to the tray without leaving the logger, clears and refocuses search so another food can be added, and keeps amount/unit edits visible before `Log selected`. Results stay above the tray on mobile; each selected row shows serving metadata plus kcal/P/C/F/alcohol, amount steppers, and a unit selector. `Review` still opens the detailed single-food amount modal when needed. Quick add takes a name plus estimated calories, protein, carbohydrates, and fat, then opens the same consumed-time and amount review while deliberately skipping reusable-note creation.

Search is deliberately local-first. Typing is debounced briefly and searches the indexed saved catalog plus curated foods without waiting on the network. Pressing Enter or choosing `Search online` explicitly adds USDA FoodData Central and, when branded search is enabled, Open Food Facts. After that bounded database pass, **Search wider with Gemini** is an explicit, slower fallback for an exact packaged product or beverage. TPS AI Gateway performs Google-grounded research and returns the actual source links; TPS Health either opens a fully editable evidence-backed review or carries identity into the Nutrition Facts camera when the serving data is absent, conflicting, low-confidence, or physically implausible. The wider route never runs on each keystroke. Known grocery brands are recognized anywhere in the typed words and moved into one canonical provider query; Open Food Facts uses a brand field when one is recognized, then runs the classic `search_terms` route only when the primary route returns no usable products. Identical concurrent searches share one request, and successful or empty results use a bounded ten-minute in-memory cache. This avoids provider calls on every keystroke and keeps repeated searches responsive while respecting the provider's search-rate limits.

Generic searches remain forgiving: common misspellings such as `mozarella` are corrected for matching/provider queries, possessives/apostrophes normalize cleanly so `breyers` can match `Breyer's`, and slight token typos—including adjacent-character swaps such as `peantu`—can still match local/curated/history candidates. Search results require usable macro data; a positive protein, carb, fat, sugar-alcohol, or alcohol value counts, while zero-filled placeholders are omitted. Multi-word matching is order-independent across title, brand, aliases, and ingredients; for example `great value steak cut` can match `Steak Cut Potato Wedges - Great Value`. The food editor exposes the existing `aliases` property as comma-separated `Search aliases`, making nicknames, store labels, and former package names editable without hand-editing YAML. Personal history and local notes rank first, then curated/common foods and closer name/brand matches. External branded products remain available for specific online searches and exact barcode paths, but do not outrank reviewed or repeatedly logged foods merely because a provider returned them. A trustworthy native gram serving is a bounded tie-breaker after identity relevance rather than a substitute for matching the requested product. Known provider misses retain reviewed curated fallbacks for common repeat groceries. Matching barcode or name/brand candidates from multiple providers collapse into one result, preferring local identity and then the best coherent labeled serving-and-nutrition pair; same-name rows with equivalent per-100g/per-100ml macros collapse as well.

`Include branded search results` is an actual provider boundary. Turning it off skips Open Food Facts and the USDA Branded data type while retaining saved foods, history, curated foods, and USDA Foundation/SR Legacy/Survey results. Exact barcode lookup remains available as an explicit branded lookup flow.

USDA search first sends one combined, all-words FoodData Central request per normalized multiword query, with the enabled Foundation, SR Legacy, Survey, and optional Branded data types in that request. If that response has no usable relevant row, one relaxed retry is allowed; single-word searches remain one request. Each request asks for at most 50 rows when branded search is enabled and 25 otherwise. Branded rows use USDA's consumer-facing brand name for display/search, retain a different corporate owner as an alias, and preserve GTIN/UPC plus ingredients. Equivalent 11-, 12-, and 13-digit provider codes collapse to the newest published FDC revision; if that newest duplicate omits any core protein/carbohydrate/fat field, TPS Health omits the duplicate instead of silently substituting an older formulation. Actual USDA network work is serialized across explicit online search, recipe ingredients, API callers, and Describe so a burst cannot outrun provider rate-limit feedback. Successful results use a five-minute bounded cache, and identical concurrent requests share one in-flight operation. HTTP 429 responses open one configured-key-stack circuit, separate from the public `DEMO_KEY` circuit, using case-insensitive `Retry-After` (one-hour fallback, capped at 24 hours); valid cached results remain readable while a circuit is open. Reordering or selecting a fallback cannot bypass that circuit: credential stacking is resilience for missing/invalid credentials, not quota pooling. Queued work re-reads SecretStorage, re-checks cached results, the circuit, and caller generation, and only then sends. Cache/in-flight identities use an internal non-logged fingerprint so a changed secret does not inherit stale credential state; no secret name or value is logged or stored in those keys. Local food and ingredient inputs debounce for 100 ms without provider traffic; a timed-out or stale explicit online search cannot start another provider phase after the active request settles.

Search results can be logged directly or used as a starting point for a new local food. `Create from this` opens the custom food form prefilled with the selected food's brand, barcode, serving, macro, image, ingredient, and note metadata so the user can edit values before saving and logging. If the reviewed item matches a saved food by canonical barcode, exact compatible name, or a direct name/alias match, TPS Health shows the candidate path, serving, and macros before any write. **Use existing** performs no note mutation; **Combine into existing** keeps the selected path and unions identity aliases while adopting the reviewed serving/nutrition pair; **Keep separate** explicitly creates a unique path. A single serialized catalog write queue rechecks candidates after concurrent work, so double taps and simultaneous scanner/API calls cannot create an accidental second note. Existing duplicate notes are never bulk-deleted or silently relinked.

`Describe` accepts ingredient-level meals with stated or approximate weights, such as a salad written as separate greens, chicken, cheese, vegetables, dressing, and gram amounts. The first pass keeps every ingredient separate, preserves explicit weights, estimates reasonable missing edible weights, and supplies conservative per-100g macro and calorie-density expectations. A second skeptical pass compares that draft against the original description, correcting only supported omissions, accidental merges/duplicates, explicit details, estimates, or search phrases before provider search begins. Provider candidates are checked against expected weight, food type, calorie density, and physically possible macro mass; candidates that appear materially high or low are rejected in favor of a clearly named `(estimated)` ingredient that remains editable. Descriptions with multiple ingredients create one meal note using the selected identity mode, linked values in the `ingredients` property, and canonical `servingUnit: meal`, calculate the meal's macros from those ingredients, and place that meal in the pending tray for final review and logging. Single-item descriptions remain individual tray entries.

Describe delegates all model messages, credentials, provider fallback, structured-output validation, and trace IDs to TPS AI Gateway. TPS Health supplies the domain prompt/schema and owns food search, plausibility checks, meal creation, and daily-note logging. When the gateway is disabled, missing, or exhausts its providers, Describe automatically uses its deterministic local parser and normal food search instead of leaving the workflow unusable. Health settings no longer contain AI provider credentials or model configuration.

The model is deliberately limited to two planning tasks: extract a structured ingredient plan, then audit that plan against the original description. The review sees no provider candidates and cannot select a candidate, choose what gets logged, or write data; a failed review retains the valid first plan. TPS code then performs provider searches, walks the already-ranked candidates in order, rejects implausible weights/calorie densities/macros, preserves supported explicit units, and chooses the first defensible match. The same deterministic matching remains available after local fallback parsing.

Food detail and barcode-review forms use a compact responsive grid. Name and brand, serving amount and unit, and nutrition fields sit side by side whenever the modal width permits, then naturally collapse as the viewport narrows. These forms use normal UI-size labels, descriptions, controls, and headings so editing a food does not read like an oversized settings screen.

Manual custom-food creation uses the same normalization path as API-created foods. Names are trimmed and required, serving amounts must be finite and greater than zero, serving units are normalized with the default `serving`, and calories are derived from macros when an explicit calorie value is not provided. Invalid manual/API inputs stop before writing a fallback `Untitled food` note or silently coercing bad serving amounts to `1`.

Provider text search stays fast and bounded, but deliberate selection through Add, Choose amount, `Create from this`, or the recipe picker enriches a barcode-backed Open Food Facts candidate from the cached fields-limited exact-product record. This recovers labeled serving fields that the text index can omit without multiplying search requests. Search-only or failed-enrichment candidates remain honest `per 100 g`/`per 100 ml` foods and default to `100 g`/`100 ml`, never a fabricated generic serving. Barcode-backed local notes with only that old generic/per-100 basis are eligible for the same guarded serving refresh; TPS Health preserves their name, aliases, notes, path, and other local identity fields while replacing the serving and nutrition together. Provider parsing preserves package units such as `bar` or `bag`, parses metric serving text such as `1 bag (32 g)` and fractional household measures such as `1/2 cup (120 ml)`, and stores the human package unit separately from the metric serving basis. Valid structured serving quantity/unit fields take precedence over free text. Explicit provider per-serving nutrients are preferred because they represent the labeled portion; a missing labeled nutrient is scaled from per-100 data only when a trustworthy metric serving exists, so partial labels cannot mix incompatible bases. Sugar alcohols from provider `polyols`/sugar-alcohol fields are stored as `sugarAlcoholG` instead of beverage `alcoholG`, and calorie derivation subtracts those grams from regular 4 kcal/g carbohydrate before applying sugar-alcohol factors; erythritol is treated as 0 kcal/g. Implausible metric serving sizes from providers or saved notes are ignored so malformed/package-level values such as `18000 ml` do not become log units or serving labels. Exact-product reads reuse the successful 30-minute barcode cache and honor the shared Open Food Facts Retry-After circuit.

Provider model:

- Local food and recipe notes are the canonical reviewed source for foods you actually log.
- Previously logged foods are boosted so repeated personal groceries outrank new external candidates.
- USDA FoodData Central is preferred for generic/common foods and stable nutrient profiles. Foundation Foods and SR Legacy are useful for non-branded foods; USDA Branded Foods updates monthly and is useful as a secondary packaged-food source.
- Open Food Facts is useful for barcode/branded coverage and images/ingredients, but its own API documentation says records are voluntarily contributed and not guaranteed accurate or complete. TPS Health treats these as candidates to review, enrich, and save locally rather than unquestioned source-of-truth rows.
- For higher-volume or more auto-updating packaged-food support, use a local cache fed by provider exports or a commercial provider with serving/measure support. The plugin should still keep a reviewed local food note once a food is logged.

The food search modal supports batch selection as the default flow. Tap a result to add it to the selected-food tray, search again, repeat, adjust each amount/unit inline, optionally edit a queued food's name/serving/macros from its tray row, optionally change the consumed time with the local date-time picker, then `Log selected` to write all entries with the same consumed timestamp. The unlogged selected-food tray is saved in the plugin's vault-backed data so an accidentally dismissed logger can be reopened and resumed for the same food-log date/target; the draft is cleared only after `Log selected` succeeds or the user presses `Clear`. Reopened drafts default the consumed-time picker to the current local time for the active target date unless a saved consumed time was edited very recently for the same day, so stale trays do not keep logging to yesterday. Editing a queued food updates the source food note or creates a local food note for provider-only items, replaces that queued item with the saved canonical food, and persists the pending tray again so synced devices restore a valid queue. Restored drafts also refresh queued source-backed foods from their vault notes before logging. Single-food review/logging uses the same `Consumed time` picker. Creating from the selected set opens a dedicated meal modal by default because selected foods represent one consumed serving unless the note is later edited as a multi-serving recipe. The created meal writes each selected food into the recipe's ingredient property, rolls those values into meal frontmatter macros, and opens in the normal log modal for review/logging. Normal searched/scanned/selected foods create or reuse durable food notes when persistence is needed; Quick add is the explicit exception and writes only the consumed-instance line. Daily summaries resolve an entry's owner day from `dailyNotePath` or its source daily-note path before timestamp fallbacks, so cross-midnight timestamps do not detach a row from the selected daily note.

When the GCM food-log button is enabled, it is shown as an apple icon-only action only when the active note exactly matches Core Daily Notes' configured folder and filename format. The same enabled-and-daily-note predicate is enforced by GCM registration, Health's visibility refresh, and the scoped tap fallback, so a stale GCM control cannot open logging from another note. Vault-root Daily Notes exclude nested date-shaped lookalikes, while formats containing path separators such as `YYYY/MM/DD` recognize their generated nested note. Health owns one layout lifecycle listener for GCM readiness and provider replacement; failed or incomplete registration is retried by that listener without accumulating callbacks, and stale provider cleanup failures cannot block a replacement registration. If logging starts from a daily note or dashboard panel with an explicit date context, the food log modal defaults the consumed date to that selected local day before writing the log entry, including when the selected day is today. Non-today contexts also offer explicit buttons for `Today` or the open note date.

The mobile tap fallback and visibility sync are scoped to Health's registered `data-tps-gcm-external-action-id="tps-health:food-log"` control. Health does not capture or mutate unrelated buttons merely because another TPS surface labels them `Log food`; dashboard-owned actions remain owned by that dashboard.

## Workout Files

A workout is one Markdown file:

```yaml
---
tpsType: health-workout
tpsHealthSchema: 1
title: "Workout 2026-05-31 10.30"
runKind: run
runType: workout
workflowType: workout
recurrenceMode: completion-triggered
workoutDate: 2026-05-31
startedAt: 2026-05-31T15:30:00.000Z
---
```

Sets are stored as plain bullet log records in the workout note body:

```md
- Bench press - 185 lb x 8 [type:: workoutSet] [setId:: set-...] [exercise:: Bench press] [reps:: 8] [weight:: 185] [unit:: lb] [rest:: 90]
```

Workout sets are always plain bullet log records, never Obsidian checkbox tasks. Live Preview and reading mode visually group contiguous bullets into compact exercise cards; source mode remains ordinary Markdown. At pane widths of 520 px or more, each set fits one lean row containing its ordinal/type, honest `Last set` result, weight, reps, rest, and **Done** state. Numeric inputs are always visible; their minus/plus steppers appear only when that field is hovered or focused, with focus-driven disclosure on touch devices. Container-driven 3/2/1-column fallbacks keep smaller split panes and phones readable without clipping. The row overflow menu contains set type, copy, adjacent superset/drop-set linking, and safe delete actions. The full-width `+ Add set` at the end of an exercise card inserts after that block and seeds weight, reps, unit, rest, and superset from its latest row while intentionally starting as a normal planned set without inheriting a drop-set link. Rest remains durable inline metadata: completing a set writes execution timestamps and `restStartedAt`. Legacy workout-set task lines remain readable but rows without a unique `setId` render read-only rather than risking a stale write.

Choosing an unknown exercise from the workout UI now creates or reuses its exercise note immediately and stores that link on the planned set. Seeded and duplicated rows preserve the exercise path; changing the row to another exercise clears a stale link. Direct API set logging still honors `createExerciseNote: false`.

The selected Daily Note is always the live workout owner. **Also create a dedicated workout note** optionally keeps the compatible whole-session record for dashboards and history, but it no longer moves the interactive workout away from the day where it happened. Individual sets can be marked `Per arm`; that marker is visible in the workout UI and stored as `[perArm:: true]` so future lifted-volume totals can count both sides without guessing. Workout records use `workoutDate` and `startedAt`; the one Daily Note navigation task additionally carries `[scheduled:: startedAt]` so Controller/calendar surfaces can find it without turning exercise-set bullets or dedicated workout notes into scheduled events.

Saved workout layouts are workflow templates and workout sessions are run instances. For compatibility, workout plan notes still use `kind: workout-plan` and workout session notes still use `kind: workout`, but new files also carry explicit workflow/run metadata: workout plans get `workflowKind: workflow`, `workflowType: workout`, `recurrenceMode: completion-triggered`, and `targetGapDays`; workout sessions get `runKind: run`, `runType: workout`, `workflowType: workout`, `workflowPath`/`workflowName` when launched from a plan, and `previousCompletedDate` plus `secondsSincePreviousCompletion` when a prior completion exists. `completion-triggered` means the next process instance is created from completion flow, not by a date scheduler. `cooldownDays`/`targetGapDays` are cadence and measurement fields used to track the gap to the next instance, while `nextEligibleDate` remains a derived display/query convenience for workout plans.

The Start workout modal leads with the saved-template choice and two explicit paths: `Start with plan` or `Start empty`. The template action stays disabled until text is entered and requires an exact existing template, preventing a mistyped name from silently creating a note. Title, optional dedicated-note creation, cooldown, and **Open Daily Note** live under the collapsed `Workout options` disclosure so the common start path stays short. Changing the selected workout day does not rebuild the form or discard input. Starting from a template inserts its exercises and planned sets under the Daily Note heading without another set-entry popup. Starting empty creates the one linked navigation task, heading, and protected control card; it does not immediately force an exercise picker. **+ Exercise** adds a planned linked row, **+ Set** opens set logging, and **End workout** completes the session and checks the navigation task. A configured dedicated workout template remains user-owned, and its set rows stay synchronized through the active-workout add/log paths. Superset and dropset grouping remains available through row overflow controls, while raw group-id inputs are omitted from set-entry modals.

Workout starts use the same Daily Note date context as food logging. The heading can be placed after properties, immediately above the first real level-2 heading (fenced examples are ignored), or at the bottom. **Above first level-2 heading** preserves every leading headerless line—including prose, tasks, and fenced examples—above the workout block. The control card shows elapsed time and performed/total progress and uses the same actions in Live Preview and Reading mode. At narrow container widths the action row becomes two columns with **End workout** spanning the full width; coarse-pointer targets are at least 44 px. Every set-producing UI/API path shares the same per-file mutation queue as row edits, so simultaneous submissions re-read the result of the preceding write instead of assigning duplicate set counts or overwriting a newly logged set. Editor events stay local to row controls, and row/block mutations re-resolve their unique `setId`; missing or duplicate ids abort with concise diagnostics rather than targeting a captured line number. Open Live Preview buffers are synchronized through their CM6 document transaction before disk writes so a stale editor cannot later overwrite an added or performed set.

The old three-way `Workout log target` control is normalized into the simpler contract: Daily Note always, with an optional dedicated workout note. Existing `daily-note` values remain daily-only; older `session-note` and `both` values retain dedicated-note creation and now also create the Daily Note section. Workout dashboards can continue querying dedicated notes by `kind: workout`/`workoutDate`/`status` without relying on `scheduled`.

`TPS Health: Log activity` records walking, running, cycling, hiking, mobility, or another simple activity as one inline daily-note bullet; it never requires a separate activity note. `Activity Log.base` combines these records with daily-note workout receipts because workouts are now an activity subtype while retaining their existing session and set behavior. Records include stable activity/source IDs plus optional duration, distance/unit, steps, calories, device, and notes. The `source`, `sourceId`, and `device` fields reserve a clean boundary for future Apple Health synchronization; Apple Health transport and deduplication are not implemented yet. The API exposes `ensureActivityLogBase()` and `logActivity()`, while `ensureWorkoutLogBase()` and the old workout Base command ID remain compatibility aliases.

## Barcode Flow

`Scan food barcode` enters the normal food logger on its Scan mode, then opens the same camera-first scanner used from the logger. A centered guide makes the useful scan region obvious, status appears with the camera instead of below a long control stack, and Flash/Flip controls appear only when they can help. Manual numeric UPC/EAN entry and image upload remain close fallbacks. On iOS, Apple's true VisionKit scanner is native app code and is not directly callable from an Obsidian community plugin webview unless Obsidian exposes a native bridge. TPS Health therefore probes for known native barcode bridge shapes, such as Capacitor barcode scanner plugins on `window`, before starting the web scanner; when no bridge exists, is cancelled, or errors, scanning continues through the web camera. The scanner also offers an `Apple Shortcut` handoff on iOS-like runtimes and watches `TPS Health Barcode Scan.md` while the scanner is open.

The live path uses ZXing's `BrowserMultiFormatOneDReader` against a requested 1920×1080 stream with UPC/EAN/CODE_128 hints and `TRY_HARDER`. Version 0.23 of the decoder expands ordinary 1D row coverage, improving labels that are away from the exact image center. Alongside the zero-copy video reader, TPS Health keeps one bounded canvas decode in flight and cycles correction angles of 0°, 22.5°, 45°, and 67.5° across full-frame and enlarged center candidates. Combined with ZXing's 90° retry and reverse-row decoding, every physical orientation is brought within 11.25° of a supported scan axis without retaining a batch of frame canvases. A native `BarcodeDetector`, when available, starts immediately at the same bounded cadence.

After the camera starts, TPS Health feature-detects continuous focus, a centered focus point, and optical zoom. Supported constraints are applied independently so one unsupported feature cannot disable scanning. The unzoomed view gets the first 650 ms for close labels; if no barcode has decoded and the camera exposes a useful zoom range, a temporary capped zoom pass helps a relatively distant label before returning to the base zoom. Every start/flip/close creates a new camera-session generation. Permission, native-bridge, video-play, decoder-start, image, constraint, and lookup results that arrive for an older or closed session are ignored, and late media streams, decoder controls, timers, and tracks are stopped instead of reviving the camera behind a closed modal. Backgrounding pauses an active web camera and only the still-open scanner resumes it. A successful read gives immediate status feedback and stops every active scanner path before lookup.

Image scanning downsizes oversized photos to a maximum 1600-pixel edge before decoding. Full-frame, cropped, contrast/threshold, and multi-angle candidates are generated and decoded sequentially rather than retained together, and decoding does not create base64 copies of every canvas. This keeps peak memory bounded on high-resolution phone photos while preserving the targeted candidates that help with small or arbitrarily oriented labels.

Scanner tests can install fake barcode scanner adapters through the modal options object instead of touching real browser/device APIs. The adapter surface covers `requestCameraStream`, `createLiveReader`, `createCanvasReader`, `createNativeDetector`, `nativeBridgeScan`, and `navigatorInfo`. When an adapter is omitted, TPS Health falls back to the live Obsidian webview behavior. Regression coverage verifies the adapter seams, generation guards, stale stream/control disposal, bounded lazy image pipeline, no-data-URL contract, and mobile/accessibility styling without opening a real camera.

Apple Shortcut setup:

1. Create an Apple Shortcut named `TPS Health Scan Barcode`.
2. Add `Scan QR or Barcode` and set it to scan barcodes.
3. Add `Open URLs` with an Obsidian URI that overwrites `TPS Health Barcode Scan.md` in this vault with the scanned value, for example `obsidian://new?vault=TishOS%20v0.1&file=TPS%20Health%20Barcode%20Scan.md&content=<Shortcut Scanned Code>&overwrite=true`.
4. If the built-in `obsidian://new` overwrite behavior is unreliable on the installed Obsidian version, the optional Advanced URI community plugin can be used instead with an overwrite URI such as `obsidian://advanced-uri?vault=TishOS%20v0.1&filepath=TPS%20Health%20Barcode%20Scan.md&data=<Shortcut Scanned Code>&mode=overwrite`.
5. Keep the TPS Health scanner modal open before running the Shortcut so the inbox watcher can receive the new note content.

After a barcode is read:

1. TPS Health normalizes the digits and checks the indexed local catalog first, including valid UPC/EAN zero-padding aliases.
2. Only a local miss reaches the Open Food Facts v2 product endpoint. Identical concurrent lookups share one request; successful results are cached for 30 minutes and confirmed misses for five minutes in a bounded in-memory cache. Timeouts and request failures are not stored as misses, so retry remains available.
3. A matched food returns directly to the existing selected-food tray without a second fetch or a forced second logging modal.
4. A confirmed provider miss opens **Scan Nutrition Facts**. The capture requests the rear camera, bounds the longest edge to 1600 pixels, and sends one compressed JPEG through the device's configured Gemini provider in TPS AI Gateway. The extracted one-serving label values remain unsaved until the user reviews and creates the food; manual entry remains available without taking a photo.

Food notes created from barcodes include source fields such as `brand`, `barcode`, `imageUrl`, serving data, and macros.

## Daily Rollups

When automatic daily rollups are enabled, each logged food recalculates daily-note frontmatter properties:

```yaml
---
consumedCalories: 520
protein: 42
carbs: 58
fat: 14
fiber: 6
sugar: 18
sodium: 620
healthUpdatedAt: 2026-06-01T15:00:00.000Z
---
```

Legacy visible rollup blocks using `<!-- tps-health-rollup:start -->` are removed the next time rollups run.

Daily frontmatter rollups only write food nutrient keys that are configured as health goals. New linked and Quick add food-log lines keep the consumed amount, serving basis, date, id, and scaled hidden macro fields inline so TPS Table/Bases can display consumed-instance values. `[nutritionSnapshot:: true]` makes those line values authoritative: later edits to the reusable food note affect future logs only and cannot change historical totals. Daily-note rollups write food energy to `consumedCalories`; legacy `cal` remains readable as the old consumed-calorie alias for existing notes and queries. Workout/run calories should use `caloriesBurned` on workout notes so intake and exercise output stay distinct. Older rows containing all nutrient fields are also treated as snapshots; an incomplete legacy row may still fall back to its linked note because the original missing values cannot be recovered retroactively.

## Food Log TPS Table View

TPS Health still owns food logging, food-note resolution, rollups, and row-level food actions, but the default `Food Log.base` now uses GCM's generic `tps-table` / **TPS Table** view instead of the old health-specific Base view. `TPS Health: Open Food Log base` and `ensureFoodLogBase()` create or repair the default file with filters for the configured food log file plus the Core Daily Notes folder. The public `getDailyFoodMacroTotals(dateIso)` API remains available for external consumers and returns canonical nutrition totals for one strict `YYYY-MM-DD` date, but Home no longer needs a separate hardcoded summary. When daily notes live at the vault root, the Base uses the broad `file.name != ""` source filter because Obsidian Bases does not return root files for `file.folder == ""`; `lineFilterKey: food` then keeps the rendered results scoped to actual food lines. The view keeps food columns, completed-date sort metadata, `totalsRow: top`, and `createAction: command` / `createCommandId: tps-health:log-food`. Repair adds the top totals default only when the option is absent, preserving explicit `off`, `top`, or `bottom` choices.

TPS Health no longer registers `tps-health-food-log`, so the retired custom Food Log view is absent from the Bases view picker. `ensureFoodLogBase()` migrates that legacy view in the default `Food Log.base` to `tps-table`; GCM also repairs its older `tps-log-table` alias to the canonical type. Native Bases still operate on source files, and GCM TPS Table scans matching Markdown inline-property lines inside those files so food logs can stay as editable Dataview-style bullets instead of becoming one file per entry.

Daily-note food bullets keep the readable amount/title visible and store machine-readable food fields inside an HTML comment. Food log rows are consumed instances, so they include scaled `cal`, `protein`, `carbs`, `fat`, and related macro fields in that hidden block for GCM TPS Table and Bases display, while the linked food note remains the editable source of truth for reusable/default serving data. Live preview replaces the raw Markdown line with a compact grid chip so clicking a logged line does not reveal the hidden fields. The food name is the primary left-aligned value, compact calorie/macro pills sit to its right, and serving/amount details form a quieter second row. On phone-sized layouts, the title and actions remain on the first row, the macro pills become a horizontally scrollable rail, and serving details stay below without squeezing or truncating the title. Reading mode keeps the normal Markdown bullet readable, and rendered/embedded food bullets remain source-aware so right-clicking a visible food log line can adjust the consumed serving, change the consumed date/time, edit the linked food note's name/macros, open the food note, or jump to the source line. Changing the consumed date updates `completedDate` and `dailyNotePath`; daily-note stored entries move to the target daily note and refresh both affected daily rollups. When multiple food log lines are highlighted in live preview or reading mode, right-clicking a selected log can create a recipe from the selected consumed entries with aggregated macros.

Known limitation: native Bases table/list views operate on files and tasks, so they cannot directly row-render arbitrary non-task Dataview food bullets. TPS Table supplies that inline-line rendering while preserving the current Markdown bullet storage model.

## Settings

Settings are normalized deterministically on load and before save. Vault-specific configuration such as custom folders, food log target/path, health goals, provider options, and API-key secret references is preserved even when it differs from source defaults. Unknown extension/newer-release fields are retained, while explicitly retired Health fields such as `foodLogHeading`, `dailyNoteFormat`, and `dailyNoteFolder` are removed. Daily-note ownership now stays entirely with Obsidian Core. A higher `settingsVersion` is treated as read-only: an older plugin may use compatible values but will not downgrade or rewrite that file. Every ordinary save reloads the latest persisted payload and applies only keys changed by the current plugin instance, so volatile food-draft and workout-state writes cannot overwrite preferences synced from another device. Health goal JSON uses one object per metric: `min` only means good at or above that value, `max` only means good at or below that value, and both `min` and `max` normalize to a healthy range regardless of the typed `kind`; reversed bounds are corrected on save.

USDA FoodData Central credentials are an ordered list of up to five device-local Obsidian SecretStorage references. The first populated reference is primary; later populated references are fallbacks. Empty device-local references are skipped, preserving synced reference order on devices that do not have every secret. Automatic rotation occurs only for exact `API_KEY_MISSING` or `API_KEY_INVALID` responses. Disabled, unverified, unauthorized, generic 403, 5xx, timeout, network-error, and 429 responses do not rotate; 403 credential status is surfaced without exposing the reference or value. If no configured reference is populated, TPS Health uses public `DEMO_KEY`.

On first load after upgrading, the former single `usdaApiKeySecret` reference is preserved as the first canonical list entry and is removed from persisted settings only after the canonical payload saves. A custom legacy plaintext `usdaApiKey` is written and read back successfully before plaintext is purged. An occupied secret containing a different value is never overwritten: migration selects an empty configured reference or appends a safe new reference while capacity remains. If no safe destination exists, or SecretStorage read/write/verification fails, TPS Health remains enabled on `DEMO_KEY`, blocks the initial sanitized migration save, preserves the plaintext field in later settings payloads, and retries after reload. The public fallback is never copied into SecretStorage. TPS Health requires Obsidian 1.12.0 or newer because this credential contract depends on SecretStorage and `SecretComponent`.

The normal test suite never spends the shared public `DEMO_KEY` quota. USDA request construction, combined data types, response parsing, cache/in-flight behavior, queue cancellation, and 429 circuits use deterministic fakes. The optional live integration runs only when `USDA_FDC_TEST_API_KEY` is supplied to the test process; the value is used only in the request and is never printed or persisted.

The scalar Calorie goal, Protein goal, and Activity goal fields are canonical for the corresponding built-in rendered metrics. Changing one updates its `healthGoals` entry before save. On load, stale bounds that still equal a TPS default are migrated to the scalar value while explicitly non-default JSON bounds are preserved in storage; rendering still uses the canonical scalar target. Additional JSON-defined metrics are unaffected.

The settings UI is a five-destination hub. Only the selected page is rendered, and the page choice is UI-only rather than another persisted setting:

- **Daily logging** hands Daily Note folder/format changes to Obsidian Core and owns the food-log target, the single-file path when relevant, section, and automatic rollups.
- **Food & goals** owns branded nutrition search, the canonical calorie/protein/activity fields, and one optional **Custom goal JSON** disclosure for labels, colors, ranges, and additional metrics.
- **Workouts** owns the workout target, daily summary link, rest behavior, cooldown default, and set notation.
- **Note library** owns reusable-note folders, identification modes, workout/exercise/food/recipe tags (including the existing **Exercise tag** value), and one optional Templates disclosure.
- **Integrations & advanced** owns the GCM food button, a direct **Open AI Gateway settings** handoff, one optional **Provider credentials** disclosure for Open Food Facts and ordered USDA references, and diagnostics.

The route hub remains visible while scrolling. Route changes focus the selected page heading, and USDA add/edit/reorder/remove rerenders preserve the active route and scroll position while moving focus to a reachable credential control. On narrow screens, the five route buttons form a horizontal strip, setting controls wrap to full width, and secret/text/JSON inputs cannot force the settings pane wider than the phone.

Reusable-note upsert diagnostics explain why an API, search clone, or modal save merged into an existing note or created a new one. Food upserts log explicit path hits/misses, masked-barcode hits or stale targets, exact name/brand hits or stale targets, final misses, and whether opening the resulting note was requested or intentionally skipped. Exercise and workout-plan upserts log explicit path hits/misses, name hits or stale targets, and misses so reports like "saving this created a duplicate" can be traced to the resolver branch instead of inferred from the final note.

Daily rollup diagnostics log update starts, input source selection, missing single-file log sources, legacy rollup block removal, and final totals. This is intended to make reports like "I logged food but the totals did not update" traceable to the actual source path and rollup route.

Inline mutation diagnostics log stale UI control targets without noisy payloads. Workout set row edits and recipe ingredient edits record missing target files, out-of-range line numbers, and successful writes so a report like "I tapped the row control but nothing changed" can be tied back to a stale rendered control or a successful note mutation.

Recipe ingredient control diagnostics log invalid quantity, missing unit, unsupported unit, missing linked-food opens, submit, not-written stale targets, done, and failed save outcomes. This makes reports like "I changed a recipe ingredient and it did not save" traceable to validation, stale rendered controls, linked-food availability, or the note write.

Automatic workout task diagnostics trace checkbox-driven flow separately from manual row controls. When a planned workout task is checked, logs record tracking registration, snapshot caching or cache failures, reentrant modify skips, workout edits with no newly checked planned set, detection source, no-change annotations, frontmatter updates, modify failures, daily receipt completion missing-file/missing-row/done outcomes, final-set finish-prompt opens, duplicate prompt suppression, and whether the prompt finished the workout, opened another set, or was dismissed.

Active-workout layout extraction diagnostics trace saved-layout content back to the source note. They log whether structured set entries came from the workout note or daily receipt, missing source files or missing daily parent rows, fallback task-name extraction, explicit empty-layout outcomes, and the final layout-entry count used to create the workout plan.

Workout action-bar diagnostics explain why note-level controls appear or disappear. Refresh logs summarize scanned leaves, Markdown views, recognized workout views, missing containers, rendered bars, removed stale bars, and skipped renders; render logs record host failures and successful bar creation/path updates.

Exercise and workout-plan diagnostics explain picker and reusable-note resolution. Exercise search and workout-plan search log result counts, find-or-create logs whether a reusable note was reused or created, and set logging records each per-file queue decision (`queuedBehindExisting`), mutation start, resolved write target, and intentional reusable-note skip. Workout set helper focus logs note open/focus success or editor availability failures, and active-workout exercise-name lookup logs no-active-workout, missing active file, and successful name counts for set modal suggestions.

Queued-food diagnostics cover the batch tray state that survives modal close/reopen. Logs record restore decisions, date/target mismatches, empty log/create-recipe attempts, queued item edit open/save/missing-entry, source-refresh no-change, draft persistence, and draft clearing so reports about disappearing or stale selected foods can be tied to the exact tray state transition.

Food-log row diagnostics cover action buttons and context menus that can otherwise fail silently after the rendered line changes. Logs record selection resolution, stale rendered line fallback, no-match menu attempts, missing linked food notes for adjust/edit/open actions, edit-food source-vs-modal handoff, serving-adjust food-note open done/failure outcomes, serving-adjust invalid/save/failure outcomes, durable line replacement and rollup follow-up, recipe/meal empty/done/failure outcomes, source-line open results, stale update/delete targets, and inserted-line focus failures.

`rollupHeading` remains a typed setting intentionally. It is used only to find and remove old visible rollup blocks when daily frontmatter rollups run; it is not a sign that source defaults and vault config need to match.

`Default food log section` is intentionally blank by default. Blank keeps food entries unheaded and inserts daily-note entries immediately after frontmatter; `Food Log` is only the settings placeholder suggestion, not the persisted default.

Every workout is anchored by a real level-2 heading in the Daily Note. **Workout position in Daily Note** selects after properties, above the first level-2 heading, or bottom; persisted legacy `workoutLogHeading` values are ignored.

## Public API

TPS Health exposes a typed API for commands, other TPS plugins, and future AI-assisted logging.

Access it from Obsidian plugin code:

```ts
const api = app.plugins.plugins["tps-health"]?.api;
```

It is also mirrored at:

```ts
const api = app.tpsHealth;
```

Current API surface:

```ts
api.getSchema()
api.searchFoods(query)
api.lookupBarcode(barcode)
api.createFood(input)
api.upsertFood(input)
api.createFoodFromLabel(input)
api.findOrCreateFood(item)
api.logFoodByName(input)
api.logFoodByBarcode(input)
api.logFoodByFoodPath(input)
api.ensureFoodLogBase()
api.searchExercises(query)
api.createExercise(input)
api.upsertExercise(input)
api.findOrCreateExercise(input)
api.searchWorkoutPlans(query)
api.createWorkoutPlan(input)
api.upsertWorkoutPlan(input)
api.findOrCreateWorkoutPlan(input)
api.logFood(input)
api.startWorkout(input)
api.finishWorkout(input)
api.logSet(input)
api.getActiveWorkoutPath()
api.getActiveWorkout()
api.getSettings()
api.getDailyRollup()
api.updateDailyRollup()
api.getMetricRenderConfigs()
api.getMetricRenderConfig(propertyKey)
api.getPropertyCatalog()
```

`createFood`, `upsertFood`, and `createFoodFromLabel` accept an optional `duplicateStrategy`. `reuse` returns the matching saved food without changing it, `combine` updates that note with the incoming reviewed serving/nutrition while preserving its path and merged aliases, and `create` deliberately writes a separate unique note. `createFood` defaults to `reuse`; callers must opt into `create` when a same-food duplicate is intentional. Barcode and direct-name collision checks are serialized across API and UI writes.

`getPropertyCatalog()` is the opt-in GCM integration contract for reusable food-note fields and automatic Daily Note rollups. Food definitions carry the current Health identification scope: tag-only uses the configured food tag, folder-only uses the configured foods folder, frontmatter-only requires `kind: food`, and the combined mode accepts any of those signals. Rollup definitions are generated only for configured food-rollup goals and require both `healthUpdatedAt` and the individual rollup key, so they do not become generic properties on unrelated notes. GCM imports a snapshot only when the user presses its Health import action; changing Health folders, tags, identification mode, or goals requires **Import / refresh** again.

Deterministic agent food logging should use a barcode or exact food note path. These calls do not accept free-text food names and do not fall back to search matching:

```ts
await app.tpsHealth.logFoodByBarcode({
  barcode: "012345678905",
  quantity: 1,
  unit: "serving",
  section: "Food Log"
});
```

```ts
await app.tpsHealth.logFoodByFoodPath({
  foodPath: "Health/Foods/Example Protein Bar.md",
  quantity: 1,
  unit: "serving",
  section: "Food Log"
});
```

`logFoodByName` and `logFood` remain available for richer plugin workflows, but low-context agents should avoid them unless a human has already resolved the target food identity.

Example workout logging:

```ts
await app.tpsHealth.startWorkout({ title: "Push day" });
await app.tpsHealth.logSet({
  exercise: "Bench press",
  reps: 8,
  weight: 185,
  weightUnit: "lb",
  rpe: 8
});
await app.tpsHealth.finishWorkout();
```

# Describe food

Describe is a mode inside the normal food logging menu. Enter a typed or dictated meal, then choose **Estimate meal**. The panel dismisses the mobile keyboard, blocks duplicate submission, and shows progress through extraction, review, and any necessary item repair. The extraction stage assigns every explicit food a stable ID and preserves amounts, units, brands, preparation methods, sizes, and order. Named prepared dishes stay together unless the description explicitly lists their ingredients, while distinct sides and drinks become separate tray items.

The second stage estimates nutrition for the whole described amount and audits confidence, calorie/macro consistency, macro mass, and calorie density. A missing or questionable item gets its own bounded retry. The final reconciliation requires every extracted ID exactly once; unresolved items stay visible with zero confidence instead of being discarded. The completed tray opens automatically and remains fully editable: change an estimate, remove or replace it, search for another food, or add more items. These `custom-inline` items are intentionally one-off estimates; editing or logging one never creates a reusable food/meal note, and nothing reaches the Daily Note before **Log selected** succeeds.

Provider credentials and models are managed centrally in TPS AI Gateway. Describe requests prefer Gemini, use small flat JSON schemas, and keep separate stable durable IDs for extraction, review, and each repair so a queued text request can resume on the requesting device. The extracted list is checkpointed before review. If Gateway is unavailable, TPS Health retains its deterministic local matching fallback, including a reviewed large-Honeycrisp serving. Diagnostics record phase, item count, retry/recovery counts, confidence summary, and outcome without logging meal text, API keys, full provider payloads, or images.

Barcode lookup remains local/curated first, then Open Food Facts. After a confirmed miss, TPS Health automatically asks Gateway's Google-grounded Gemini route to check manufacturer, retailer, distributor, and label evidence. Coherent complete nutrition opens an editable review; an uncertain or identity-only result seeds **Scan Nutrition Facts** instead of inventing macros. Label images remain device-local and require Gemini on that device. Manual creation remains available when the provider or camera is unavailable.

## Settings layout

TPS Health uses five shallow routed pages: **Daily logging**, **Food & goals**, **Workouts**, **Note library**, and **Integrations & advanced**. Only Custom goal JSON, Templates, and Provider credentials use optional disclosures; there are no nested accordions.
