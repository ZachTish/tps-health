## Mobile modal contract

## Health UI service contract

Health exposes its cross-plugin UI integration through the workspace events `tps:health-ui-api-request`, `tps:health-ui-api-available`, and `tps:health-ui-api-unavailable`. The immutable protocol-v1/API-v1 descriptor publishes a frozen `supportedHomeActionIds` snapshot and six bounded methods: `executeHomeAction`, `prepareFoodDescription`, `ensureLogBase`, `getMetricRenderConfigs`, `isWorkoutFile`, and `openFoodLogEntryMenu`. Home execution, Describe, Base ensure, and food-row menu opening are Promise-based; metric configuration and workout classification are synchronous reads. Boundary values are bounded serializable records and strings, never Obsidian `App`, `TFile`, DOM elements, mouse events, modal instances, or private runtime objects. Consumers validate own data properties, reject accessors and inherited capability shapes, bind exact descriptor/API source identity, and clear only the matching generation.

Home requests carry the selected ISO date and exact Daily Note path. `executeHomeAction` is asynchronous: Health re-resolves that file against the effective Daily Notes folder and filename format before opening food, activity, or workout UI, without consulting the active workspace file or choosing another date candidate. Missing, non-Markdown, unsafe, or date-mismatched contexts reject. If the modal date remains unchanged, submission retains and rechecks the exact path; changing the submitted date intentionally releases that binding and resumes normal date resolution. Describe validates at entry and again immediately before food-note, meal-note, or pending-draft mutation.

Describe ownership is per loaded plugin generation. Identical public requests share one promise, while divergent public requests and competing native/service entrypoints fail before entering a second mutation worker. AI failure may use the deterministic local parser only before Health begins a food-note, meal-note, or pending-draft mutation; after that boundary the original failure is surfaced without starting a second flow. Reload starts a fresh generation instead of pretending to serialize uncancellable work from an old plugin instance. Retained service and legacy-API wrappers reject after unload, while already-issued Vault or AI operations cannot be physically cancelled. No exactly-once guarantee is made across an application crash.

Food-row menu handoff is similarly exact: index plus raw line is preferred, then one unique stable food ID, then one unique exact raw line. Ambiguous or stale rows fail closed. Updates and deletes re-resolve at the atomic `Vault.process` write boundary, and Open log line re-resolves after the file opens before moving the cursor. Health opens the menu from the supplied source snapshot and plain screen coordinates; it does not require a synthetic `MouseEvent` or adopt GCM's multi-row selection. The temporary legacy App alias is generation-fenced and remains only for provider-first rollout compatibility; new consumers must use the workspace service.

## GCM integration service contract

Health discovers optional GCM capabilities only through `tps:gcm-integration-api-request`, `tps:gcm-integration-api-available`, and `tps:gcm-integration-api-unavailable`. The synchronized protocol-v1/API-v1 contract exposes four bounded operations: external-action registration, shared Markdown opening, note-timer start, and file-specific note-timer stop. Cross-plugin values are frozen relative Markdown paths, canonical ISO instants, explicit open policy, fixed display policy, and validated status records. Obsidian objects, DOM nodes, `Date`, leaf factories, private plugin instances, and mutable service objects never cross this boundary.

Discovery is one request plus exact lifecycle announcements, not polling. A GCM replacement first withdraws the old descriptor, which disposes Health's exact old action, then announces the replacement and causes one fresh registration. Retained action callbacks compare both the Health generation and GCM source identity before opening UI. The action context owns the clicked file path, so another active split cannot redirect a food log to the wrong day. GCM owns action rendering and visibility evaluation; Health does not capture document taps, inspect GCM data attributes, or mutate GCM elements after render.

GCM is optional. With no current provider, food and workout logging remain available but no GCM action or new timer effect is claimed. Workout-note opening chooses the public GCM opener before acting when that provider is current; absence, or an explicit pre-open decline, uses Obsidian's supported `WorkspaceLeaf.openFile` route. A rejected or withdrawn GCM call is reported and is not replayed through a second opener because the first provider may already have crossed an effect boundary.

The mixed-version window is degraded, not feature-identical. Stable GCM with optimized Health can still call Health through its temporary alias, but optimized Health cannot register its food action or automatic timer with stable GCM and uses native workout opening. Optimized GCM with stable Health retains old Health-to-GCM calls through GCM's temporary root API, but GCM cannot use stable Health for Home food/activity/workout actions, Describe, Base repair, metrics, workout classification, or food-row menus. Release Health first only when no workout or timer is active, update GCM immediately afterward, then smoke-test the intermediate and final states. BRAT remains the normal production transport.

Automatic workout timing is exact-session and retry-safe within the supported lifecycle. Health derives the session ID from the durable workout ID and saves it together with the canonical workout start before requesting start. Finish saves a pending cleanup record before requesting stop, then clears that record only after the current provider confirms `stopped` or `not-running` and the cleared state is saved successfully. Provider absence, replacement, a rejected response, or failed settings persistence leaves cleanup intact for the next provider announcement or workout start. GCM can stop this owned session even when ordinary time tracking was disabled after start, and immutable path plus session snapshots let cleanup survive a workout-note rename or deletion. Health never routes owned cleanup through a generic active-timer stop or a path-only guess. While cleanup remains unresolved, a later workout remains usable but skips its optional automatic GCM timer rather than owning two uncertain sessions.

One legacy compatibility behavior is intentionally removed: an active workout created before this upgrade without a persisted GCM session ID is marked unowned, and Health performs no path-only or generic provider stop. Path alone cannot prove which timer Health owns. Finish or stop any active workout timer before updating; if one spans the upgrade, it may require one manual stop in GCM. New workouts, including backdated starts, persist an exact session ID and canonical start instant and retain automatic exact cleanup. An unresolved retired-provider start is tracked in memory for the current Health instance, but cannot be durably transferred across a Health instance reload; no cross-instance or crash-level exactly-once claim is made.

Moving a food entry to another Daily Note uses a target-first, idempotent protocol because Obsidian has no cross-file transaction. The destination is inserted with `Vault.process` and keyed by the entry's stable `foodId`; an exact existing destination is treated as a safe retry, while a divergent duplicate ID or legacy row without an ID fails closed. Source removal is a second strict `Vault.process` step. If that removal fails after destination commit, Health deliberately leaves both copies and reports a recoverable partial move so retry can converge without risking loss of the only entry.

TPS Health treats daily notes as the durable health log and uses linked notes for reusable foods, recipes, and workout sessions.

See `DESIGN.md` for the broader researched workflow model covering food, recipes, meals, exercises, routines, serving sizes, and AI-assisted command flows.

## Daily Note Lines

Food logs are appended to the selected day's daily note body by default. The optional food heading setting can still route entries into a section, and the older single-file food log remains supported for legacy readback and tests, but daily notes are the active storage target for normal logging and Home-launched logging:

```md
- 1 serving - [[Health/Foods/Greek yogurt|Greek yogurt]] <!-- [type:: foodLog] [food:: Greek yogurt] [qty:: 1] [unit:: serving] [servings:: 1] [foodPath:: Health/Foods/Greek yogurt.md] [foodId:: food-...] [createdDate:: 2026-06-01T15:00:00.000Z] -->
```

Workout summaries are appended to the selected day's daily note body. TPS Health does not create or target a workout heading in daily notes; headings are left for manual organization after logging:

```md
- [tps-health:workout path="Health/Workouts/Workout 2026-05-31 10.30.md" startedAt=2026-05-31T15:30:00.000Z] [[Health/Workouts/Workout 2026-05-31 10.30]]
```

These lines are plain Dataview inline fields so they are easy to type manually and query without plugin state. Generated linked-food entries store the consumed instance, scaled known nutrients, source metadata, barcode, serving metadata, timestamps, and notes. Reusable nutrition, brand, source, barcode, serving metadata, and ingredient details still live on the linked food note as the editable source of truth. If both local food-note nutrition and inline macro fields are present, the inline macro fields are treated as explicit per-instance overrides so manual edits are reflected in rollups.

## Food And Recipe Notes

Reusable foods and recipes are Markdown files with frontmatter:

```yaml
---
tpsType: health-food
tpsHealthSchema: 1
name: "Greek yogurt"
servingAmount: 1
servingUnit: serving
calories: 120
proteinG: 15
carbsG: 8
fatG: 2
---
```

Recipes use `kind: recipe` and keep their ingredients directly in the body as simple linked bullets such as `- 1 egg - [[Health/Foods/Egg|Egg]]`. Recipe frontmatter stores `recipeServings` for the full ingredient list and saves per-serving macro totals so logging `1 serving` uses the correct fraction of the full recipe. Meals use `kind: meal`; they live in the recipes folder, use the same ingredient-line body format, and are fixed to `recipeServings: 1` with `servingUnit: meal`. TPS-created recipe and meal notes normalize plain ingredient names into linked food-note bullets when an exact saved food match exists. Live Preview and reading mode upgrade ingredient bullets into guarded controls with labeled Qty, Unit, Food, and Macros fields; Live Preview replaces the raw linked bullet with the same bar-style control while the cursor is off that line, then reveals source Markdown when the line is selected. Changing quantity/unit rewrites only that simple ingredient line and refreshes recipe frontmatter nutrition. The recipe renderer exposes `+ Ingredient`, which searches foods, saves provider items as local food notes when needed, writes a linked metric ingredient line, and refreshes recipe nutrition. Food macros are always computed from the linked food note and selected amount/unit without adding per-ingredient macro fields. Unresolved plain ingredients show that no linked food note was found. Food, recipe, and meal notes are returned by the food logger search, and the current food/recipe note can be edited with `TPS Health: Edit current food/recipe`.

Contract invariant: a meal is the recipe composition model fixed to one serving, not a separate multi-serving structure. Canonical meal values are `kind: meal`, `recipeServings: 1`, `servingAmount: 1`, and `servingUnit: meal`; its full ingredient total is its single-serving nutrition. Conflicting meal yield, metric-serving, or serving-unit fields are ignored when a meal is read and normalized whenever it is written. Use `kind: recipe` whenever the ingredient list represents more than one serving.

Editing an existing food, recipe, or meal always asks how existing links should behave. `Update linked instances` modifies the current entity note so existing food logs and recipe ingredients keep their path and receive source-level changes. `Create new version` writes a new unique entity path, returns that new entity to the active tray/editor callback, and leaves every historical link on the old path untouched. Cancel performs no write. Exact future barcode/name resolution prefers the newest matching entity so a newly versioned food becomes the default without rewriting history.

Editing a logged meal opens its full single-serving composition in the food editor. Each ingredient row shows quantity, unit, linked food, and calculated calories/macros; quantities and units can be adjusted, an ingredient can be removed, or `+ Add ingredient` can search saved/provider foods and choose a supported amount/unit. A selected ingredient updates the rows and meal preview locally; provider results are not saved as food notes until the parent meal is saved. Save then reuses or creates each linked food note and applies the same `Update linked instances` versus `Create new version` decision as other source-note changes. Cancel leaves the meal and provider candidates untouched. A logged meal instance continues to link to its existing source unless the caller explicitly adopts a newly versioned meal.

## Food Search And Creation

Barcode results returned by an exact lookup are added to the tray as already-enriched records, so TPS Health does not fetch the same Open Food Facts item a second time. Remote barcode candidates have a five-second recoverable timeout, and a 13-digit EAN beginning with zero also tries the corresponding valid 12-digit UPC. ZXing is the primary live web decoder; the heavier cropped-canvas fallback starts only when live ZXing startup fails, rather than decoding the same camera stream concurrently. My foods/recipes also reuses one usage-history scan for both local ranking and recent/frequent grouping.

`Log food` opens as a tray-first logger with three options: Barcode, Search, and My foods/recipes. Selecting Barcode opens the scanner immediately and starts the camera without an extra scan/start click; matched barcode foods are added back into the same selected-food tray. The scanner includes Flash and Flip camera controls when the camera is active, with flash depending on browser/media-track torch support. It probes for an exposed native barcode bridge on mobile/iOS-like runtimes before starting the web scanner, offers an explicit Apple Shortcut handoff on iOS-like runtimes, then tries native `BarcodeDetector` when available and ZXing with food-barcode hints over full-frame, cropped, upscaled, processed, and rotated candidates so small UPC/EAN labels are more likely to decode. The Barcode tab still keeps manual UPC/EAN lookup available, and the scanner modal still offers manual entry plus image scanning as fallbacks. Barcode lookups require usable macro data before they are treated as successful provider matches. Search is the external and local food database search tab, and active inline food drafts seed this search with their parsed query and amount. My foods/recipes shows recent/frequent foods plus saved local food and recipe notes without running an external search. Tapping a result adds it to the inline selected-food tray without leaving the logger, clears and refocuses search so another food can be added immediately, and keeps amount/unit edits visible in the same flow before `Log selected`. New search results render above the selected-food tray so queued items cannot hide the next result list on mobile. Each selected row shows serving metadata plus kcal/P/C/F/alcohol for the currently selected amount and unit, with minus/plus amount steppers and a unit selector, so the user can verify and adjust the line before writing it. `Review` still opens the single-food amount modal when a detailed one-item review is needed. Search covers local food/recipe notes, previously logged foods, curated common foods, USDA FoodData Central, and Open Food Facts branded products. Branded provider search is enabled by default for normal search because grocery-store packaged foods are usually branded; ranking, token matching, personal-history boosts, and broad-query filters control noise instead of hiding the provider database. Open Food Facts is queried through both its search service and its classic `search_terms` endpoint so normal product-name searches have a fallback when one route misses or returns a transient provider error. Generic searches are intentionally forgiving: common misspellings such as `mozarella` are corrected for matching/provider queries, possessives/apostrophes normalize cleanly so `breyers` can match `Breyer's`, slight token typos can still match local/curated/history candidates, curated common foods and unbranded USDA foods are promoted, and unlogged Open Food Facts or USDA branded products are hidden for broad or weak matches unless they strongly match the query or are already in personal history. Search results must include usable macro data, so macro-less local/provider candidates and zero-filled placeholder foods are filtered before ranking and display; a positive protein, carb, fat, sugar-alcohol, or alcohol gram value counts as macro data, so alcohol items such as whiskey and sugar-alcohol foods still work when their nutrients are real. Multi-word searches are token-set based, so words can be out of order across product title, brand, aliases, and ingredients; for example `great value steak cut` can match `Steak Cut Potato Wedges - Great Value`. Search strongly boosts personal history and local notes, then curated/common foods and closer name/brand token matches; external branded products remain available for specific queries and exact barcode paths, but they no longer outrank reviewed local or repeated foods merely because a provider returned them. Known provider misses can be covered by curated fallbacks, such as Great Value Shredded Hash Browns, Kraft Original Macaroni & Cheese Dinner, Hidden Valley Original Ranch Dressing, Tyson White Meat Chicken Nuggets, Pepperidge Farm Goldfish Cheddar Crackers, and Nature Valley Oats 'n Honey Granola Bars, so common repeat foods stay available even when USDA/Open Food Facts do not return the exact branded SKU. Matching barcode or name/brand candidates from multiple providers are collapsed into one result, preferring local notes and then the most complete candidate. Same-name results with matching per-100g/per-100ml macros are also collapsed so duplicate serving variants do not crowd the list.

`Include branded search results` is an actual provider boundary. Turning it off skips Open Food Facts and the USDA Branded data type while retaining saved foods, history, curated foods, and USDA Foundation/SR Legacy/Survey results. Exact barcode lookup remains available as an explicit branded lookup flow.

USDA search sends one combined FoodData Central request per normalized query, with the enabled Foundation, SR Legacy, Survey, and optional Branded data types in that request. Actual USDA network work is serialized across normal search, recipe ingredients, autocomplete, and Describe so a burst cannot outrun provider rate-limit feedback. Successful results use a five-minute bounded cache, and identical concurrent requests share one in-flight operation. HTTP 429 responses open one configured-key-stack circuit, separate from the public `DEMO_KEY` circuit, using case-insensitive `Retry-After` (one-hour fallback, capped at 24 hours). Reordering or selecting a fallback cannot bypass that circuit: credential stacking is resilience for missing/invalid credentials, not quota pooling. Queued work re-reads SecretStorage, re-checks the circuit and caller generation, and only then sends. Cache/in-flight identities use an internal non-logged fingerprint so a changed secret does not inherit stale credential state; no secret name or value is logged or stored in those keys. Food and ingredient search inputs debounce for 450 ms, and a timed-out/stale USDA search cannot start another provider phase after the active request settles.

Search results can be logged directly or used as a starting point for a new local food. `Create from this` opens the custom food form prefilled with the selected food's brand, barcode, serving, macro, image, ingredient, and note metadata so the user can edit values before saving and logging. Saving from this flow upserts the local food by barcode or exact name/brand, then opens the log modal for that canonical local instance instead of creating a duplicate copy.

`Describe` accepts ingredient-level meals with stated or approximate weights, such as a salad written as separate greens, chicken, cheese, vegetables, dressing, and gram amounts. The first pass keeps every ingredient separate, preserves explicit weights, estimates reasonable missing edible weights, and supplies conservative per-100g macro and calorie-density expectations. A second skeptical pass compares that draft against the original description, correcting only supported omissions, accidental merges/duplicates, explicit details, estimates, or search phrases before provider search begins. Provider candidates are checked against expected weight, food type, calorie density, and physically possible macro mass; candidates that appear materially high or low are rejected in favor of a clearly named `(estimated)` ingredient that remains editable. Descriptions with multiple ingredients create one `kind: meal` note containing linked ingredient bullets, calculate the meal's macros from those ingredients, and place that meal in the pending tray for final review and logging. Single-item descriptions remain individual tray entries.

Describe delegates all model messages, credentials, provider fallback, structured-output validation, and trace IDs to TPS AI Gateway. TPS Health supplies the domain prompt/schema and owns food search, plausibility checks, meal creation, and daily-note logging. Health discovers the Gateway only through its versioned public workspace request/available/unavailable contract; it no longer reads an App-object monkeypatch or Obsidian's private plugin registry. The synchronized consumer client accepts a Gateway that loads after Health, snapshots and binds the validated public methods, ignores malformed or stale lifecycle announcements, and clears discovery when either plugin unloads. When the gateway is disabled, missing, or exhausts its providers before Health begins a mutation, Describe uses its deterministic local parser and normal food search instead of leaving the workflow unusable. Once ingredient-food creation, meal creation, or pending-draft persistence has begun, a later failure is surfaced without starting a second local flow. Health settings no longer contain AI provider credentials or model configuration.

The model is deliberately limited to two planning tasks: extract a structured ingredient plan, then audit that plan against the original description. The review sees no provider candidates and cannot select a candidate, choose what gets logged, or write data; a failed review retains the valid first plan. TPS code then performs provider searches, walks the already-ranked candidates in order, rejects implausible weights/calorie densities/macros, preserves supported explicit units, and chooses the first defensible match. The same deterministic matching remains available after local fallback parsing.

Food detail and barcode-review forms use a compact responsive grid. Name and brand, serving amount and unit, and nutrition fields sit side by side whenever the modal width permits, then naturally collapse as the viewport narrows. These forms use normal UI-size labels, descriptions, controls, and headings so editing a food does not read like an oversized settings screen.

Manual custom-food creation uses the same normalization path as API-created foods. Names are trimmed and required, serving amounts must be finite and greater than zero, serving units are normalized with the default `serving`, and calories are derived from macros when an explicit calorie value is not provided. Invalid manual/API inputs stop before writing a fallback `Untitled food` note or silently coercing bad serving amounts to `1`.

Open Food Facts search results are enriched from the full barcode product record before logging or cloning. This improves serving units such as `bar` or `bag`, parses metric serving text such as `1 bag (32 g)`, and stores the human package unit separately from the metric serving basis. When grams/ml are known, explicit provider per-serving nutrients are preferred because they represent the labeled portion; per-100g/per-100ml scaling is used only when a serving value is missing. Sugar alcohols from provider `polyols`/sugar-alcohol fields are stored as `sugarAlcoholG` instead of beverage `alcoholG`, and calorie derivation subtracts those grams from regular 4 kcal/g carbohydrate before applying sugar-alcohol factors; erythritol is treated as 0 kcal/g. Implausible metric serving sizes from providers or saved notes are ignored so malformed/package-level values such as `18000 ml` do not become log units or serving labels.

Provider model:

- Local food and recipe notes are the canonical reviewed source for foods you actually log.
- Previously logged foods are boosted so repeated personal groceries outrank new external candidates.
- USDA FoodData Central is preferred for generic/common foods and stable nutrient profiles. Foundation Foods and SR Legacy are useful for non-branded foods; USDA Branded Foods updates monthly and is useful as a secondary packaged-food source.
- Open Food Facts is useful for barcode/branded coverage and images/ingredients, but its own API documentation says records are voluntarily contributed and not guaranteed accurate or complete. TPS Health treats these as candidates to review, enrich, and save locally rather than unquestioned source-of-truth rows.
- For higher-volume or more auto-updating packaged-food support, use a local cache fed by provider exports or a commercial provider with serving/measure support. The plugin should still keep a reviewed local food note once a food is logged.

The food search modal supports batch selection as the default flow. Tap a result to add it to the selected-food tray, search again, repeat, adjust each amount/unit inline, optionally edit a queued food's name/serving/macros from its tray row, optionally change the consumed time with the local date-time picker, then `Log selected` to write all entries with the same consumed timestamp. The unlogged selected-food tray is saved in the plugin's vault-backed data so an accidentally dismissed logger can be reopened and resumed for the same food-log date/target; the draft is cleared only after `Log selected` succeeds or the user presses `Clear`. Reopened drafts default the consumed-time picker to the current local time for the active target date unless a saved consumed time was edited very recently for the same day, so stale trays do not keep logging to yesterday. Editing a queued food updates the source food note or creates a local food note for provider-only items, replaces that queued item with the saved canonical food, and persists the pending tray again so synced devices restore a valid queue. Restored drafts also refresh queued source-backed foods from their vault notes before logging. Single-food review/logging uses the same `Consumed time` picker. Creating from the selected set opens a dedicated meal modal by default because selected foods represent one consumed serving unless the note is later edited as a multi-serving recipe. The created meal writes each selected food directly into the note body, rolls those ingredient lines into meal frontmatter macros, and opens in the normal log modal for review/logging. Normal food logging does not expose a separate `Save as my food` step because logged foods already create/reuse durable food notes when persistence is needed. Daily summaries resolve an entry's owner day from `dailyNotePath` or its source daily-note path before timestamp fallbacks, so cross-midnight timestamps do not detach a row from the selected daily note.

When the GCM food-log button is enabled, it is registered through the current workspace service as an apple icon-only action only on recognized daily notes. GCM owns rendering, cleanup, and visibility refresh; Health owns the exact clicked-file validation and food UI. If logging starts from a daily note or dashboard panel with an explicit date context, the food log modal defaults the consumed date to that selected local day before writing the log entry, including when the selected day is today. Non-today contexts also offer explicit buttons for `Today` or the open note date.

## Workout Files

A workout is one Markdown file:

```yaml
---
tpsType: health-workout
tpsHealthSchema: 1
title: "Workout 2026-05-31 10.30"
runKind: run
runType: workout
workflowType: workout
recurrenceMode: completion-triggered
workoutDate: 2026-05-31
startedAt: 2026-05-31T15:30:00.000Z
---
```

Sets are stored as plain bullet log records in the workout note body:

```md
- Bench press - 185 lb x 8 [type:: workoutSet] [setId:: set-...] [exercise:: Bench press] [reps:: 8] [weight:: 185] [unit:: lb] [rest:: 90]
```

Workout sets are always plain bullet log records, never Obsidian checkbox tasks. Live Preview and reading mode visually group contiguous bullets into compact exercise cards; source mode remains ordinary Markdown. Each row shows its set ordinal/type, the honest `Last set` values from the same exercise earlier in the current session, weight, reps, rest, and `Play`/`Performed`. The row overflow menu contains set type, copy, adjacent superset/drop-set linking, and safe delete actions. The full-width `+ Add set` at the end of an exercise card inserts after that block and seeds weight, reps, unit, rest, and superset from its latest row while intentionally starting as a normal planned set without inheriting a drop-set link. Rest remains durable inline metadata: `Play` writes execution timestamps and `restStartedAt`. Legacy workout-set task lines remain readable but rows without a unique `setId` render read-only rather than risking a stale write.

Unknown exercises are now promoted into exercise notes automatically when a set is logged, unless the API caller passes `createExerciseNote: false`.

Workout storage is configurable. Workout-note mode keeps full workout runs in dedicated notes; Daily-note-only mode treats workout plans/notes as the reusable workout UI and writes the concrete run, planned exercises, and logged sets into the selected daily note. Individual sets can be marked `Per arm`; that marker is visible in the workout UI and stored as `[perArm:: true]` so future lifted-volume totals can count both sides without guessing. Both modes use `workoutDate` and `startedAt` rather than generic `scheduled` metadata, so workout records do not become unrelated scheduled tasks/events.

Saved workout layouts are workflow templates and workout sessions are run instances. For compatibility, workout plan notes still use `kind: workout-plan` and workout session notes still use `kind: workout`, but new files also carry explicit workflow/run metadata: workout plans get `workflowKind: workflow`, `workflowType: workout`, `recurrenceMode: completion-triggered`, and `targetGapDays`; workout sessions get `runKind: run`, `runType: workout`, `workflowType: workout`, `workflowPath`/`workflowName` when launched from a plan, and `previousCompletedDate` plus `secondsSincePreviousCompletion` when a prior completion exists. `completion-triggered` means the next process instance is created from completion flow, not by a date scheduler. `cooldownDays`/`targetGapDays` are cadence and measurement fields used to track the gap to the next instance, while `nextEligibleDate` remains a derived display/query convenience for workout plans.

The Start workout modal leads with the plan choice and two explicit paths: `Start with plan` or `Start empty`. The plan action stays disabled until text is entered and requires an exact existing plan, preventing a mistyped name from silently creating a note. Title, storage, cooldown, and open-note controls live under the collapsed `Workout options` disclosure so the common start path stays short. Changing the selected workout day does not rebuild the form or discard input. Starting from a plan opens the populated workout surface without another set-entry popup. Start empty opens the created workout and shows the slim exercise picker once; choosing an exercise appends its first planned blank set, closes the picker, scrolls the stable `setId` card into view, and focuses its weight control without selecting or exposing the backing Markdown row. Generated workout notes contain frontmatter and the configured workout tag but do not impose a `Sets` heading or per-exercise headings. Logged and planned set bullets append directly to the workout body in deterministic order. A configured workout template remains the user-owned body structure; TPS Health appends records without injecting its retired default section/layout modes. Superset and dropset grouping remains available through the row overflow controls, while raw group-id inputs are omitted from set-entry modals.

Workout starts use the same daily-note date context as food logging. In Daily-note-only mode, the selected daily note is the canonical run owner and the plan supplies the reusable UI/placeholder exercises; set logging and finish updates stay nested under that daily-note workout instance. In Workout-note mode, the dedicated workout note remains canonical. Opening a generated workout note delegates by path to the current public GCM integration service when available, so workouts follow the same unpinned-tab reuse rules as other time-tracked notes instead of pinning the workout tab; provider absence or an explicit decline uses the supported Obsidian opener. The sticky workout header is the single session surface: it shows elapsed time and performed/total progress, opens one slim `+ Exercise` picker that appends the first planned blank set and closes, provides the primary `Finish` action, and keeps `Save as layout` in the overflow menu. It does not open the weight/reps logging popup. Every set-producing UI/API path shares the same per-file mutation queue as row edits, so simultaneous submissions re-read the result of the preceding write instead of assigning duplicate set counts or overwriting a newly logged set. Editor events stay local to row controls, and row/block mutations re-resolve their unique `setId`; missing or duplicate ids abort with concise diagnostics rather than targeting a captured line number. Open Live Preview buffers are synchronized through their CM6 document transaction before disk writes so a stale editor cannot later overwrite an added or performed set.

The intended storage/rendering model is selected by `Workout log target`: `Workout note` makes the session note canonical, `Daily note only` makes the selected daily-note instance and its nested set lines canonical, and `Workout note + daily receipt` writes both. Workout dashboards should query `kind: workout`/`workoutDate`/`status` and support either source rather than relying on `scheduled`.

`TPS Health: Log activity` records walking, running, cycling, hiking, mobility, or another simple activity as one inline daily-note bullet; it never requires a separate activity note. `Activity Log.base` combines these records with daily-note workout receipts because workouts are now an activity subtype while retaining their existing session and set behavior. Records include stable activity/source IDs plus optional duration, distance/unit, steps, calories, device, and notes. The `source`, `sourceId`, and `device` fields reserve a clean boundary for future Apple Health synchronization; Apple Health transport and deduplication are not implemented yet. The API exposes `ensureActivityLogBase()` and `logActivity()`, while `ensureWorkoutLogBase()` and the old workout Base command ID remain compatibility aliases.

## Barcode Flow

`Scan food barcode` opens a camera scanner with manual UPC/EAN entry and image upload fallbacks. In the food logger, choosing the Barcode tab opens this scanner and starts the camera immediately. On iOS, Apple's true VisionKit scanner is native app code and is not directly callable from an Obsidian community plugin webview unless Obsidian exposes a native bridge. TPS Health therefore probes for known native barcode bridge shapes, such as Capacitor barcode scanner plugins on `window`, before starting the web scanner; when no bridge exists, is cancelled, or errors, the status notes that the web camera scanner is being used and scanning continues normally. The scanner also shows an `Apple Shortcut` button on iOS-like runtimes. That button opens a Shortcut named `TPS Health Scan Barcode`; while the modal is open, TPS Health watches `TPS Health Barcode Scan.md` for a newly written numeric barcode, then sends it through the same barcode lookup flow and marks the inbox note processed so it does not loop. While scanning, `Flash` toggles torch mode on browsers/devices that expose it, and `Flip camera` restarts the stream against the opposite facing camera. The live scanner uses ZXing's `BrowserMultiFormatOneDReader` against the active video element as the primary continuous decoder with UPC/EAN/CODE_128 hints and short retry delays. If that path does not find a barcode quickly, a bounded backup loop tries guarded native `BarcodeDetector` support and ZXing over lower-center, center, side, upscaled, processed, and rotated canvas candidates. Keeping the barcode steady, well lit, and centered improves reliability.

Scanner tests can install fake barcode scanner adapters through the modal options object instead of touching real browser/device APIs. The adapter surface covers `requestCameraStream`, `createLiveReader`, `createCanvasReader`, `createNativeDetector`, `nativeBridgeScan`, and `navigatorInfo`. When an adapter is omitted, TPS Health falls back to the live Obsidian webview behavior: `navigator.mediaDevices.getUserMedia`, known native bridge globals, `BarcodeDetector`, and ZXing reader constructors. This keeps production scanning unchanged while allowing deterministic tests to exercise camera start, native bridge success/fallback, native detector, image/canvas decode, and platform-specific button logic without opening a real camera or constructing live scanner implementations.

Apple Shortcut setup:

1. Create an Apple Shortcut named `TPS Health Scan Barcode`.
2. Add `Scan QR or Barcode` and set it to scan barcodes.
3. Add `Open URLs` with an Obsidian URI that overwrites `TPS Health Barcode Scan.md` in this vault with the scanned value, for example `obsidian://new?vault=TishOS%20v0.1&file=TPS%20Health%20Barcode%20Scan.md&content=<Shortcut Scanned Code>&overwrite=true`.
4. If the built-in `obsidian://new` overwrite behavior is unreliable on the installed Obsidian version, the optional Advanced URI community plugin can be used instead with an overwrite URI such as `obsidian://advanced-uri?vault=TishOS%20v0.1&filepath=TPS%20Health%20Barcode%20Scan.md&data=<Shortcut Scanned Code>&mode=overwrite`.
5. Keep the TPS Health scanner modal open before running the Shortcut so the inbox watcher can receive the new note content.

After a barcode is read:

1. TPS Health checks Open Food Facts by barcode.
2. The user reviews the returned product values.
3. The user can create a local food note and immediately log it, or log without saving.
4. If a local note already has the same `barcode`, TPS Health reuses that note instead of creating a duplicate.

Food notes created from barcodes include source fields such as `brand`, `barcode`, `imageUrl`, serving data, and macros.

## Daily Rollups

When automatic daily rollups are enabled, each logged food recalculates daily-note frontmatter properties:

```yaml
---
consumedCalories: 520
protein: 42
carbs: 58
fat: 14
fiber: 6
sugar: 18
sodium: 620
healthUpdatedAt: 2026-06-01T15:00:00.000Z
---
```

Legacy visible rollup blocks using `<!-- tps-health-rollup:start -->` are removed the next time rollups run.

Daily frontmatter rollups only write food nutrient keys that are configured as health goals. Linked food log lines keep the consumed amount, serving count, food path, date, id, and scaled hidden macro fields inline so TPS Table/Bases can display consumed-instance values. Rollups still resolve from the linked food note first and treat inline macro fields as per-instance overrides, so later title or macro edits on the source note are reflected unless the row was explicitly edited as an instance. Daily-note rollups write food energy to `consumedCalories`; legacy `cal` remains readable as the old consumed-calorie alias for existing notes and queries. Workout/run calories should use `caloriesBurned` on workout notes so intake and exercise output stay distinct. Legacy lines with inline macro fields remain readable for compatibility.

## Food Log TPS Table View

TPS Health still owns food logging, food-note resolution, rollups, and row-level food actions, but the default `Food Log.base` now uses GCM's generic `tps-table` / **TPS Table** view instead of the old health-specific Base view. `TPS Health: Open Food Log base` and `ensureFoodLogBase()` create or repair the default file with filters for the configured food log file plus daily-note folders. The public `getDailyFoodMacroTotals(dateIso)` API remains available for external consumers and returns canonical nutrition totals for one strict `YYYY-MM-DD` date, but Home no longer needs a separate hardcoded summary. When daily notes live at the vault root, the Base uses the broad `file.name != ""` source filter because Obsidian Bases does not return root files for `file.folder == ""`; `lineFilterKey: food` then keeps the rendered results scoped to actual food lines. The view keeps food columns, completed-date sort metadata, `totalsRow: top`, and `createAction: command` / `createCommandId: tps-health:log-food`. Repair adds the top totals default only when the option is absent, preserving explicit `off`, `top`, or `bottom` choices.

TPS Health no longer registers `tps-health-food-log`, so the retired custom Food Log view is absent from the Bases view picker. `ensureFoodLogBase()` migrates that legacy view in the default `Food Log.base` to `tps-table`; GCM also repairs its older `tps-log-table` alias to the canonical type. Native Bases still operate on source files, and GCM TPS Table scans matching Markdown inline-property lines inside those files so food logs can stay as editable Dataview-style bullets instead of becoming one file per entry.

Daily-note food bullets keep the readable amount/title visible and store machine-readable food fields inside an HTML comment. Food log rows are consumed instances, so they include scaled `cal`, `protein`, `carbs`, `fat`, and related macro fields in that hidden block for GCM TPS Table and Bases display, while the linked food note remains the editable source of truth for reusable/default serving data. Live preview replaces the raw Markdown line with a compact grid chip so clicking a logged line does not reveal the hidden fields. The food name is the primary left-aligned value, compact calorie/macro pills sit to its right, and serving/amount details form a quieter second row. On phone-sized layouts, the title and actions remain on the first row, the macro pills become a horizontally scrollable rail, and serving details stay below without squeezing or truncating the title. Reading mode keeps the normal Markdown bullet readable, and rendered/embedded food bullets remain source-aware so right-clicking a visible food log line can adjust the consumed serving, change the consumed date/time, edit the linked food note's name/macros, open the food note, or jump to the source line. Changing the consumed date updates `completedDate` and `dailyNotePath`; daily-note stored entries move to the target daily note and refresh both affected daily rollups. When multiple food log lines are highlighted in live preview or reading mode, right-clicking a selected log can create a recipe from the selected consumed entries with aggregated macros.

Known limitation: native Bases table/list views operate on files and tasks, so they cannot directly row-render arbitrary non-task Dataview food bullets. TPS Table supplies that inline-line rendering while preserving the current Markdown bullet storage model.

## Settings

Settings are normalized deterministically on load and before save. Vault-specific configuration such as custom folders, food log target/path, health goals, provider options, and API-key secret references is preserved even when it differs from source defaults. Health goal JSON uses one object per metric: `min` only means good at or above that value, `max` only means good at or below that value, and both `min` and `max` normalize to a healthy range regardless of the typed `kind`; reversed bounds are corrected on save. Obsolete persisted fields that are no longer part of `TPSHealthSettings`, including the legacy `foodLogHeading`, are stripped during this migration pass.

USDA FoodData Central credentials are an ordered list of up to five device-local Obsidian SecretStorage references. The first populated reference is primary; later populated references are fallbacks. Empty device-local references are skipped, preserving synced reference order on devices that do not have every secret. Automatic rotation occurs only for exact `API_KEY_MISSING` or `API_KEY_INVALID` responses. Disabled, unverified, unauthorized, generic 403, 5xx, timeout, network-error, and 429 responses do not rotate; 403 credential status is surfaced without exposing the reference or value. If no configured reference is populated, TPS Health uses public `DEMO_KEY`.

On first load after upgrading, the former single `usdaApiKeySecret` reference is preserved as the first canonical list entry and is removed from persisted settings only after the canonical payload saves. A custom legacy plaintext `usdaApiKey` is written and read back successfully before plaintext is purged. An occupied secret containing a different value is never overwritten: migration selects an empty configured reference or appends a safe new reference while capacity remains. If no safe destination exists, or SecretStorage read/write/verification fails, TPS Health remains enabled on `DEMO_KEY`, blocks the initial sanitized migration save, preserves the plaintext field in later settings payloads, and retries after reload. The public fallback is never copied into SecretStorage. TPS Health requires Obsidian 1.12.0 or newer because this credential contract depends on SecretStorage and `SecretComponent`.

The normal test suite never spends the shared public `DEMO_KEY` quota. USDA request construction, combined data types, response parsing, cache/in-flight behavior, queue cancellation, and 429 circuits use deterministic fakes. The optional live integration runs only when `USDA_FDC_TEST_API_KEY` is supplied to the test process; the value is used only in the request and is never printed or persisted.

The scalar Calorie goal, Protein goal, and Activity goal fields are canonical for the corresponding built-in rendered metrics. Changing one updates its `healthGoals` entry before save. On load, stale bounds that still equal a TPS default are migrated to the scalar value while explicitly non-default JSON bounds are preserved in storage; rendering still uses the canonical scalar target. Additional JSON-defined metrics are unaffected.

The settings UI uses direct collapsible sections with descriptive titles for diagnostics, daily-note storage, reusable note folders, templates, GCM integration, workout logging, food logging, nutrition sources, goals, and API settings.

## Public API

TPS Health exposes a typed API for commands, other TPS plugins, and future AI-assisted logging.

Access it from Obsidian plugin code:

```ts
const api = app.plugins.plugins["tps-health"]?.api;
```

It is also mirrored at:

```ts
const api = app.tpsHealth;
```

Current API surface:

```ts
api.getSchema()
api.searchFoods(query)
api.lookupBarcode(barcode)
api.createFood(input)
api.upsertFood(input)
api.createFoodFromLabel(input)
api.findOrCreateFood(item)
api.logFoodByName(input)
api.logFoodByBarcode(input)
api.logFoodByFoodPath(input)
api.ensureFoodLogBase()
api.searchExercises(query)
api.createExercise(input)
api.upsertExercise(input)
api.findOrCreateExercise(input)
api.searchWorkoutPlans(query)
api.createWorkoutPlan(input)
api.upsertWorkoutPlan(input)
api.findOrCreateWorkoutPlan(input)
api.logFood(input)
api.startWorkout(input)
api.finishWorkout(input)
api.logSet(input)
api.getActiveWorkoutPath()
api.getActiveWorkout()
api.getSettings()
api.getDailyRollup()
api.updateDailyRollup()
api.getMetricRenderConfigs()
api.getMetricRenderConfig(propertyKey)
```

Deterministic agent food logging should use a barcode or exact food note path. These calls do not accept free-text food names and do not fall back to search matching:

```ts
await app.tpsHealth.logFoodByBarcode({
  barcode: "012345678905",
  quantity: 1,
  unit: "serving",
  section: "Food Log"
});
```

```ts
await app.tpsHealth.logFoodByFoodPath({
  foodPath: "Health/Foods/Example Protein Bar.md",
  quantity: 1,
  unit: "serving",
  section: "Food Log"
});
```

`logFoodByName` and `logFood` remain available for richer plugin workflows, but low-context agents should avoid them unless a human has already resolved the target food identity.

Example workout logging:

```ts
await app.tpsHealth.startWorkout({ title: "Push day" });
await app.tpsHealth.logSet({
  exercise: "Bench press",
  reps: 8,
  weight: 185,
  weightUnit: "lb",
  rpe: 8
});
await app.tpsHealth.finishWorkout();
```

# Describe food

Describe is a mode inside the normal food logging menu. Enter a typed or dictated meal, then choose `Build tray`. The Describe panel stays open, dismisses the mobile keyboard, disables duplicate submission, and reports the current preparation phase. When preparation succeeds, TPS Health opens the completed tray automatically. If preparation fails, the original description remains in place with a `Try again` action. Closing the panel while preparation runs lets the job finish without unexpectedly reopening the modal; the saved tray is available the next time Food Log opens.

When TPS AI Gateway is available through the validated public service contract, Describe uses two structured planning passes. The first extracts distinct foods, explicit amounts, brands, and ordered search queries. The second audits that draft against the original description and returns a complete corrected plan only when it finds a supported amendment; it cannot see or select provider candidates. TPS Health then runs the resulting queries concurrently through local foods, prior-use ranking, USDA, and Open Food Facts, and deterministically accepts the first plausible candidate for each planned food. If the audit is unavailable or malformed, TPS Health uses the valid first-pass plan; if the gateway is unavailable, it uses the deterministic local parser. The resulting foods are persisted in the ordinary pending tray. A completion notice includes `Open tray`, where quantities can be edited, foods removed or replaced, more foods searched and added, or the reviewed selection logged. Nothing is written to the Daily Note before `Log selected`.

Describe treats the user's quantity and unit as the consumed serving, independently from a provider's nutrition basis. The plan estimates total edible grams for the specific food and preparation. TPS Health prefers a provider's native unit when it matches and has a plausible weight; otherwise it keeps the user's unit in the tray and log while scaling the matched food's gram-based nutrition to the contextual estimate. For example, `1 piece salmon sashimi` remains `1 piece`; a credible per-piece database serving can supply its weight, while a generic 100 g result is scaled to the estimated weight of one ordinary sashimi piece. Multi-food meals write these adapted ingredient amounts in grams so recipe rollups remain computable from their linked food notes.

Provider credentials, models, fallback order, and AI diagnostics are managed centrally in TPS AI Gateway. Describe requests use strict JSON-schema output. Diagnostics log phases, counts, routes, confidence rejection, and outcomes without logging meal text, API keys, or full provider payloads.

When Describe runs on a TPS user-role device, TPS AI Gateway syncs its structured planning request to the Controller instead of attempting local Ollama on the user device. The Describe progress panel can remain open while the Controller processes the request; the schema-validated result syncs back into the same flow. The extraction pass is silent and the final review pass sends one privacy-safe `Food Describe` completion or failure message through TPS Notifier. Provider credentials never enter the queue, though the queued request text is necessarily present in the user's synced `_assets/TPS AI Queue` Markdown job and follows the Gateway's documented retention policy.
