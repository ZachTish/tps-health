# TPS Health 4.2.6

Backward-compatible food-search performance and rejected-promise ownership correction; minimum Obsidian 1.12.0.

## Change and ownership

After the existing barcode, minimum-length and already-running guards accept a submission, its local and combined database searches share one request-local usage-history promise. Both branches are launched immediately. The combined search still starts enabled providers before awaiting history; the local branch resolves the supplied promise before ranking. Existing callers that supply a Map or omit usage input retain their behavior. The public Health API shape/version and saved-food reader are unchanged.

The initial typed-local stage and its delayed automatic submission still obtain separate current snapshots. Independent submissions do not reuse history, so edits and deletions in the existing native projection are visible to the next request. No persistent cache, modal field, timer, watcher, setting, schema, migration or repair is added.

The local branch catches failure only around its awaited local search, rejects stale query/tab reporting, logs and returns without an error panel or status mutation. The concurrent online branch retains its existing error status and finally-owned loading/button cleanup. Completed combined results still reject slower local rendering; queued query, tab change and close invalidation remain intact.

## Regression evidence

The new test composes the actual FoodSearchModal submission, actual plugin history normalization and actual native getFoodUsageEntries with synthetic indexed records and constant-time link resolution. Catalog/providers and the DOM are host facades; native index setup is not part of this search-path test. At 37, 1,000 and 10,000 logs, one accepted submission previously performed two materializations and 2N record/link visits. It now performs one materialization and N visits. Both versions perform zero vault inventories, metadata lookups and raw/cached source reads in this boundary. These are deterministic operation counts, not physical-device latency measurements.

The original baseline had five expected failures across 11 checks. An added shared-history rejection check demonstrated an existing unowned local rejection while online loading already cleared. The final 13 new checks cover operation counts, distinct current snapshots, typed-local versus delayed-submit freshness, concurrent provider startup while history is pending, slower-local precedence, new query, close, tab change, online failure, shared-history rejection and barcode/minimum-length/already-running guards. Both branches receive the same promise before it is immediately rejected and settle without an escaping local rejection or stuck loading state. All 13 new and 39 existing search checks pass.

The mandatory separate build-only check passed with byte-identical artifacts; the subsequent ordinary production-mode build deployed only changed main.js and manifest.json to Obsidian Plugin Test Vault after an exact CLI name/path guard. Because the private Modal class is not a public API, three reviewed, hash-guarded source methods are compiled into an isolated class with provider/catalog/status/render facades; no live Modal is opened or patched. At 37, 1,000 and 10,000 logs, each accepted submission has one usage materialization and N record/link visits, zero inventories/metadata/source I/O/mutations, a distinct fresh second snapshot after deletion, concurrent provider startup before pending history settles, and settled shared-history rejection with the existing online status and loading controls. Real method/map references, settings, data and installed artifacts remain unchanged. Synthetic rejection intentionally emits the existing FoodSearch error log; it is not a runtime failure.

The first scratch probe aborted because this CLI renderer cannot require('obsidian'). A scratch-only correction used an exact TFile constructor from an already-owned indexed record, without an inventory; the corrected probe passed. Neither attempt changes shipped source or runtime behavior.

Combined hidden, unfocused Live Preview QA passed 13 phases, including six tab switches and two remounts.
