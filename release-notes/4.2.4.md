# TPS Health 4.2.4

Backward-compatible performance correction; minimum Obsidian 1.12.0.

## Change

Food-definition body edits and repeated metadata events now compare the consumed serving and nutrient fields with Health's existing cached definition before recalculating historical linked food logs. Only exact scalar equality authorizes skipping. Non-scalar consumed values remain conservative because the existing shallow snapshot cannot prove their contents unchanged.

Real serving or nutrient changes still project current nutrition and use the existing deferred persistence. Log quantity or source edits retain their normal projection route. Core and extra nutrients include the current configured and archived custom keys. Registering a new custom nutrient uses the existing settings-triggered configuration rebuild, which reindexes consumption records with that registry.

Existing notifications remain for eligible linked entries so body, title and recipe-component consumers stay current. The shared existing portion calculation preserves invalid/unsupported-portion rejection without recalculating nutrients. A changed resolved link destination still takes the normal projection path. No additional cache, watcher, timer, setting, schema, API, note writer or migration is introduced.

## Regression evidence

- Six focused checks failed on the released 4.2.3 source before the guard.
- Actual-service scaling regression: 1,000 linked logs, one body modification followed by metadata and 20 repeated metadata deliveries. Redundant nutrient projections fall from 22,000 to zero. The 22,000 existing record notifications are retained, with zero persistence schedules, scans or raw reads and one scoped cached read.
- Every built-in core and extra nutrient changes individually; serving amount/unit/grams/ml, configured and archived custom amounts, known zero/removal, nested inputs, raw scalar type changes, late registry configuration, invalid portions, titles, rename, deletion/replacement, changed host link resolution and log quantity/source changes remain covered.
- Complete native-record suite: 138 passed, zero failed or skipped.

The scale regression executes the actual Health service against in-memory Obsidian/GCM boundaries. Its notification subscribers do not render the full UI. The installed Test vault currently has 37 linked logs, with no more than three attached to one definition; the 1,000-log fixture is a scaling reproduction. These counts do not establish the cause or resolution of the user's reported multi-second mobile/Windows freezing.

## Installed validation

The exact methods from loaded Health 4.2.3 and 4.2.4 were replayed on separate service objects with synthetic maps/records and mocked metadata, provider, notifications and persistence. Twenty-two equivalent body/title/metadata passes against 1,000 linked logs changed from 22,000 projections to zero. Both versions retained 22,000 notifications and zero persistence requests; 4.2.4 also retained the existing indexed record objects. Changing calories from 200 to 250 still made 1,000 projections and 1,000 persistence requests with updated values. Delivering that same change again made zero projections/persistence requests in 4.2.4 instead of the earlier 1,000 repeated projections. The real service and settings were unchanged. This replay creates no files and does not exercise real UI subscribers or disk persistence; the native-record tests cover invalid portions, custom nutrients, lifecycle and actual mocked GCM writes.

Combined installed Live Preview QA ran with Health 4.2.4, GCM 7.3.10 and Navigator 8.2.2. Thirteen phases included three first mounts, six tab switches, two remounts and idle controls. Observed Macros and Activity widgets showed the expected saved data, with no render errors, phase errors, long tasks or note-mutation attempts. Three UUID Inbox display fixtures retained their bodies and moved directly to `_archive`; original navigation, observers, settings and active-workout state were restored. Some background workspace-state writes remained; they were recorded separately from note writes. One initial attempt stopped at the older probe's version guard before fixture creation; extending only that diagnostic guard allowed the unchanged QA flow to run.

The desktop window was hidden/unfocused, the plugin was warm and dates were explicit. Reading mode, implicit mapped Daily Note recognition, disclosure expansion, active-workout controls, provider actions, real food edits and physical-device gestures were outside this combined navigation check. Counts establish removal of the repeated projection work and retained functional behavior, not foreground frame latency, cold startup or resolution of the entire multi-second freezing report. Physical iPhone/iPad/Windows responsiveness remains unverified.
