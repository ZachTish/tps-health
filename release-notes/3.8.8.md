# TPS Health 3.8.8 — Food portions and consumed dates

Backward-compatible plugin correctness fixes. Minimum Obsidian: **1.12.0**. Tested in the isolated test vault and ready for the user's BRAT pull; not directly installed in production.

## Fixed at the source

- **Gram portions changed after logging.** The food logger computed nutrition from an explicit gram amount but saved the original descriptive quantity. For example, 300 g could calculate 600 kcal while persisting 1 bowl; native indexing then replaced it with the bowl's 200 kcal. The logger now saves the same gram quantity used for its calculation. Ordinary portions without a gram override retain their chosen unit.
- **Multi-serving labels used different denominators.** A food whose label describes two servings could calculate 100 kcal for one serving in the logger but 200 kcal after indexing. Native projection now uses the food's serving amount when units match, consistent with the logger and metric portions.
- **Consumed-time changes could leave food on the old day.** Food history, totals and change notifications now prioritize the consumed timestamp over the redundant legacy date. Both affected days receive the existing change notification. Date-only older records remain readable; reading does not rewrite date properties.

Includes the preceding 3.8.7 fix for food records missing when Health starts before GCM's record provider is ready.

No new settings, schema fields, API versions, migrations, polling, retries or automatic repair. No TishOS app/widget, Relay, other-plugin or production-record changes. Linked-food projections retain their existing update ownership.

## Validation

- **565 passed, 0 failed, 1 skipped** in the full declared `npm test`. The skip is the optional credential-dependent live USDA check. Five new tests cover gram handoff, serving denominators, legacy-date edits, combined lifecycle and late-arriving linked definitions. The three defect regressions failed before the runtime corrections.
- TypeScript and a separate `npm run build` pass. Test-vault deployment and named Health-only disable/load-manifests/enable verify version 3.8.8. The final separate build after the README edit is byte-identical to the tested bundle.
- Installed comparison invokes the actual `logFood`, GCM API v6 creation and native index against two synthetic food definitions. 3.8.7 computes 600/100 kcal but saves and displays 200/200. 3.8.8 saves and displays 600/100, with the gram record retaining 300 g. The real provider writes isolated synthetic Markdown records; no provider network calls or production foods are used. Its destination root/layout are redirected in memory only for the probe and restored in `finally`; settings are never saved.
- Installed edit changes the 600 kcal record to 150 g on the following day: the original day becomes 100 kcal, the new day 300 kcal, and both dates are announced. A Health reload preserves those values. Archiving the edited record leaves the new day at zero and the other day at 100. The same public macro totals API used by consumers returns the remaining 100 kcal. The redundant legacy-date precedence is specifically tested in the synthetic native-service regression; the installed GCM writer canonicalizes the fixture's extra legacy date on edit.
- Unit lifecycle coverage also verifies custom property keys, UTC timestamps resolving to the local day, linked-definition changes, late definition arrival, persisted macro projections, reload and archive. Those harnesses mock the vault/GCM boundary and use no raw body reads; late definition arrival uses no cached body reads either. This is not a production performance measurement.
- Existing consumer plugins remain enabled; no outbound provider/import automation is enabled and Obsidian Sync stays disabled in the test vault. Health, GCM, Controller, Calendar and Finances settings remain byte-identical. Test fixtures are archived after validation and temporary probes removed from the app.
- Existing block-render tests pass. This patch has no visual layout change; new visual-UI and physical-phone/iPad verification are not claimed. No UI mutation was performed against the active production window.

## Limitations

Previously logged gram overrides may never have stored their intended weight. The patch cannot safely reconstruct that missing input, and does not guess or bulk-rewrite history. Incorrect historical portions need an explicit correction from the actual amount consumed. This bounded food-tracking audit does not establish that every unrelated Health feature is defect-free.
