# TPS Health 3.8.2

New native workouts use GCM's existing fresh-ID API instead of verifying a locally generated ID against the entire vault. Health adopts GCM's persisted UUID for its active state, index and completion log. This is a backward-compatible creation performance patch; minimum Obsidian remains **1.12.0**. GCM **3.3.0+** supplies the optional fresh-creation capability; older versions retain their existing creation behavior and cost.

The change consists of selecting the already-supported fresh option at the workout creation call and logging the returned ID. Schedule fields, filenames, timer ordering, saved plans, note-opening preferences, legacy inline workouts and imported activity identities are unchanged. Failed creation rejects without a second write. No settings/schema migration, cache, watcher, background verification, repair or retry is added.

## Scope and remaining latency

This removes the global scan from **new workout creation only**. Existing-record resolution and mutation still verify authoritative identity sources. With a cold index, the first set edit, saved-plan population or Finish can therefore pay that cost. The measured first Finish did exactly that. This release does **not** claim lower total verification work, a complete workout-performance fix, native-equivalent speed, startup improvement or resolution of the reported file-naming lag.

## Validation

- 96 focused native-record/workout tests passed. New coverage verifies 25 fresh creations with one creator call each, returned identity/schedule/session data, no Health raw/cached reads in the facade, exact capability detection, older-provider compatibility and one rejected write without a retry. The actual startup test retains create → save → timer → plan ordering and checks adoption of the returned ID.
- Full versioned declared suite: **536 passed, zero failures, one optional live USDA test skipped** without its credential. TypeScript and the suite's build-only build passed under Node 24.19.0. A separate normal production build deployed only main.js/manifest.json changes to Obsidian Plugin Test Vault; named Health/GCM reloads verified the installed versions.
- Actual foreground command-palette **Start workout → Start empty → rendered Finish** in the installed test vault, with other enabled consumers retained, measured the following. Native creation includes shared GCM work; Start includes settings persistence, timer startup and opening. Each column is one instrumented desktop sample, not a distribution.

The first 3.8.2 Finish spent 2356 ms verifying sources; moving creation off that path does not eliminate the existing first-mutation requirement. Cold refers to GCM's authoritative source index after a normal plugin reload, not application/filesystem/timer caches. Timer lookup was preflighted. Read/count spans overlap unrelated event processing and must not be summed as exclusive CPU time. A 122 ms task during baseline Start and a 142 ms task during new Start remain; later capture tasks also include operator dwell/background work. No long tasks occurred in the repeated capture. Modal-open time, physical iPhone, cold process startup, saved-plan population, first set entry and a plugin-free native baseline are not covered by this installed comparison.

Time tracking was temporarily enabled with source-note storage so the synthetic timer wrote only to its owned workout. Each uniquely named fixture was allocated under Inbox; no provider, external automation or production vault was used. The final notes retained the correct identity/title/schedule/session, reached complete status, and cleared active state/timer. All mutation attempts stayed within owned fixtures. Hooks were removed, prior active-leaf state restored and folders archived directly. All five monitored plugins' settings files and installed artifact hashes remained byte-identical within each capture. An earlier baseline had opening disabled and an incorrect DOM selector; it is retained as diagnostic evidence and excluded from the table.

The final separate normal build after documentation is byte-identical to the tested artifact. This release is tested in the isolated vault and ready for the user's BRAT pull and acceptance; it is not installed in production by this work.
