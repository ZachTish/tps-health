# TPS Health 4.4.0

Set your BMR and let each day's configured activity notes determine the additional calories in your energy estimate. The new **BMR + activity notes** method reads notes selected by a property value or tag and uses configurable calories/date properties. Fixed and Calculated retain their behavior and defaults.

This is an additive minor release. Minimum Obsidian remains **1.12.0**. It changes only the Obsidian Health plugin; no Apple app, widget or import service changes.

## Configure

Open **Health → Food & goals → Energy estimate**, select **BMR + activity notes**, enter BMR, choose a property/value or tag, and choose **Save energy settings**. The chosen source's controls appear directly beside the selector. Fields remain editable without changing notes, and draft edits are saved only by the explicit button. Existing settings routes/disclosures and mobile layout are preserved; status is announced, inputs are labeled and the button regains focus after save.

The six configurable source settings are:

- `energyActivityIdentificationMode`: `property` (default) or `tag`.
- `energyActivityPropertyKey`: `kind` by default.
- `energyActivityPropertyValue`: blank by default; enter the exact value that identifies activity.
- `energyActivityTag`: blank by default; a leading `#` is optional.
- `energyActivityCaloriesPropertyKey`: `caloriesBurned` by default; choose active calories in kcal.
- `energyActivityDatePropertyKey`: `completedDate` by default; choose the actual activity date/datetime.

Property values match exactly in a scalar or list. Keys are resolved case-insensitively; ambiguous duplicate case variants are ignored. Tags match case-insensitively, including descendants in frontmatter or cached inline tags, while excluding prefix collisions. Each matching file contributes once, including a repeated list value or the same tag present in both locations. A note with the configured Health archive field set to `true` is excluded.

Finite nonnegative numbers and numeric strings are accepted as measured activity calories; zero is valid. Missing/invalid measurements or dates are ignored without guessing another property. ISO date-only values retain their date; timestamps use the local calendar day. Choose individual activities **or** a daily active-calorie summary: matching overlapping records adds their authored values rather than guessing an overlap. Do not select total daily burn that already includes BMR.

## Estimate and ownership

The selected-day estimate is **BMR + matching activity calories**, with BMR alone on a valid empty day once indexing is complete. It adds neither the activity factor nor the existing native activity/workout total. The overview shows the sum and count of matching notes; the seven-day comparison uses the same dated projection. Missing/invalid source configuration remains unknown. Missing metadata retains accepted evidence while readiness stays pending; an apparently empty day stays unavailable until indexing can prove it has no matching entries. Unlogged movement is not estimated. Current BMR applies to all displayed dates; there are no dated BMR profiles.

This projection is read-only: no TDEE property, identities, new tags or note migration is written. Matching ordinary notes requires no native identity or GCM authority for the energy projection. Existing food/workout mutation ownership and dashboard provider requirements remain; absent native authority is still shown honestly as loading/partial. Only physical metadata/source authorizes configured energy matching; decoded native aliases cannot invent field presence.

The existing cooperative discovery and metadata/rename/delete owners maintain transient path/date projection maps. No additional poller, timer, body-reading pass or routine-edit inventory is added. A source-selector save reuses one existing configuration rebuild. BMR-only changes and switching between Fixed and Calculated cause none. The feature preserves fixed/calculated saved values and ignores hidden activity inputs when those methods are selected.

Settings schema **9** reuses the future-schema guard to protect this configuration against older devices overwriting it. Existing defaults and mode are preserved on upgrade; once schema-9 settings are saved, update older devices before editing them. Save/validation failure restores the prior energy fields. Failure in a projection/UI callback after successful persistence keeps the committed in-memory and stored settings consistent. No automatic note repair, migration or reclassification runs.

## Installed verification and limitations

**The foreground installed test-vault flow used all eight active TPS consumers and two isolated ordinary activity notes without native IDs. A saved property/list selector and BMR 1,600 produced 2,050 kcal from 450 activity calories; a direct calorie edit changed the daily and seven-day views to 2,450 without refresh. Moving the edited note to the prior date changed today to 1,750 and the prior day to 2,300. Saving a parent tag matched nested frontmatter tags; a measured-zero edit retained one contributing entry with a 1,600-kcal baseline, and renaming it retained the total. Actual settings accessibility and computed styles confirmed inactive multiplier/fixed/property controls are hidden in tag mode. The final 4.4.0 plugin reload preserved the saved tag method and reconstructed both days from saved notes (today: one zero-calorie entry/BMR 1,600; prior day: 700 activity calories). Original energy settings and the prior leaf were restored; all pre-existing normalized settings matched except the expected schema 8→9 upgrade, and the six new fields were restored to their defaults. Both owned fixtures were archived byte-identically, with their bodies preserved. Every other captured TPS settings file remained byte-identical; Health persisted only its expected schema/new defaults and QA-restored values. No provider requests, production mutations or physical iPhone QA were performed.**.

No production installation, physical iPhone interaction or end-to-end latency is claimed. This is an estimate derived from the user's recorded active calories, not measured full-day expenditure. Actual coverage depends on the selected note identifiers, calorie fields and dates. Native food/dashboard readiness still depends on its existing providers.
