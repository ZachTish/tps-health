# TPS Health 4.3.2

Health startup and metadata discovery now calculate linked-food nutrition for display without rewriting notes. Explicit Health creation, portion edits, and food/recipe edits own stored nutrition. Pending dashboard updates share one aggregation, and hidden restored dashboards wait until shown. Disabled food actions skip unrelated menu refreshes.

This is a backward-compatible patch to startup performance and existing write ownership. No settings, note migration, new polling or cache is added. Minimum Obsidian remains **1.12.0**.

## Behavior and dependency

Linked portion and definition persistence requires **TPS GCM 8.1.0** with the additive `nativeRecords.updateFromSource` capability. Update GCM before Health. The public native API remains version **6**; older GCM retains reading and ordinary creation, but linked edits report a clear upgrade error instead of bypassing native write authority.

Creation prepares linked nutrition in its initial payload. Explicit portion edits compute nutrition against the current quantity, unit and link at GCM's existing source-preserving atomic boundary. Explicit food/recipe edits publish successfully committed definition evidence immediately and await changed linked entries through the existing reverse-link index after body work succeeds. Current configured identity, collision, title, timestamp and property mappings retain GCM ownership. Direct portion edits remain user actions; downstream definition fan-out remains automation and honors configured path/tag/template exclusions. No new queue, retry, repair or fallback writer is added.

Direct Base/raw-frontmatter edits update derived Health display without automatically rewriting the stored nutrient snapshot. A consumer of stored nutrition sees the last authored snapshot until an explicit Health edit saves it. Reindexing the last linked entry retains current definition evidence until the accepted replacement; changed/deleted last links remove unreferenced evidence. Reversed definition callbacks consume the newest committed evidence.

Daily widgets and the dedicated Health view share one pending aggregation per child and one latest follow-up. Hidden/disconnected children defer aggregation and rendering, then catch up on the existing visibility/layout events; hidden active-workout clocks stop. Visibility checks, listeners and timers use the container's owning document/window, including visible popouts while the main document is hidden. Disposal removes that child's listener and timers. Restored view opening returns without awaiting the native index. Disabled/unregistered GCM food actions skip menu refreshes; disabling an existing registration retains cleanup. Readiness/loading behavior and saved disclosure/settings data are preserved.

## Installed verification and limits

The actual installed Health/GCM check passed seven phases in the visible, focused TEST vault. An unchanged fan-out performed zero computed calls or source-process attempts. After an explicit source quantity edit, real Health rediscovery displayed derived **1,050** while stored nutrition stayed **700**, with zero subsequent discovery writes.

Stale-ID, protected-field and archived-entry refusal checks preserved the target source. Native identity/classification/title, authored YAML comments and flow-list formatting, the body including Unicode text, and the reusable definition body remained intact. Temporary settings objects and pass-through instrumentation were restored; all eight saved settings files remained byte-identical, the original leaf was retained, and both owned fixtures moved directly from Inbox to `_archive` byte-identically. No settings-save or unowned-write attempts occurred, and no provider calls were used. Phase IO counters include the fixture setup and verification reads; rediscovery is a real index/configuration pass, not a plugin/app reload. Installed dashboard burst/popout interaction was not separately exercised by this harness; actual-child source tests cover it.

Five **30-second foreground warm-start captures** of the combined GCM 8.1.0, Controller 3.1.8, Health 4.3.2 and Navigator 8.2.5 candidates measured median initial-body milestones **10.868 → 8.514 seconds**, GCM readiness **14.886 → 9.187 seconds**, and Health readiness **15.123 → 9.471 seconds**. Aggregate startup reads increased: raw **36 → 44**, cached **34 → 73–74**; recorded repeated inventory calls remained **three**. These are combined-change results, not an isolated Health benchmark or evidence that startup performs no IO.

One baseline CPU sample and one quiet candidate sample recorded Navigator self CPU **1,494 → 780 ms**, Controller **406 → 26 ms**, and its named debounce callback **367 → 0 ms**. A test process resumed during the baseline capture; this is supporting source-attribution evidence, not a controlled CPU/timing comparison. Neither warm run showed Navigator bootstrap additions/updates/removals or preview/image regeneration. Health/GCM/Finance/Calendar/Linter data stayed byte-identical; Controller persisted its previously missing existing attachmentSync default, and sync-request state may change normally; Navigator's only data change was its existing `lastShownVersion` acknowledgement, whose restoration to baseline 8.2.4 reproduced the original hash.

No full cold application start, production startup, physical iPhone/iPad interaction or first-input latency was measured. These changes do not claim to resolve every remaining startup/navigation cost. No production vault was accessed for this implementation or QA; production installation and physical-device acceptance remain separate user steps.
