# TPS Health 3.7.4

Health now builds its startup metadata index once and lets layout readiness hydrate only the indexed workout records. This removes the duplicate full-vault pass and repeated body hydration caused by metadata resolution followed by a queued layout callback. Warm plugin activation also avoids a second immediate layout pass.

Legacy workout bodies still hydrate after layout, fresh metadata events retain authority over older pending reads, and explicit configuration changes keep their full rebuild. No settings, APIs, stored schema, automatic repairs or migration change. Minimum Obsidian: **1.12.0**. This patch is scoped to Health startup ownership; it does not claim that all startup or navigation work is eliminated.

Five focused startup assertions reproduced the old duplicate work; all 82 native-record tests pass after the fix. The final versioned declared suite passes 512 tests with zero failures and one optional live USDA check skipped without its credential. TypeScript and the suite build pass under Node 24.19.0/npm 10.9.2. A separate normal build deployed only the changed main.js and manifest.json to Obsidian Plugin Test Vault; a named disable/loadManifest/enable reload verified 3.7.4. Cold metadata lifecycle and warm complete-cache activation are covered by regressions. Physical mobile startup and cold process launch are unverified; a runtime without a private initialized flag which hot-enables Health before layout after its last metadata-resolution event may wait for the next resolution event.

Installed foreground warm renderer captures, with GCM 3.6.7 and Navigator 7.0.5 enabled, show one full Health metadata pass and 85 cached workout reads. The prior event ordering performed two full passes and 170 workout reads. Whole-capture Markdown enumerations decreased from ten to nine and cached reads from 254 to 169. The individual remaining pass was approximately 150 ms; first visible synthetic content remained about 2.83 seconds. Operation counts are distinct from timings and this is not a native-parity or production-speed claim.

Installed ordinary create/edit/rename checks produced zero Health source refreshes or reads. A synthetic workout was discovered, updated from five to twelve reps and renamed with its ID and body preserved; its two refreshes used cachedRead with one core cache-fill read. Seven plugin settings files remained byte-identical, original note/search state was restored, temporary profiling hooks were removed and owned Inbox fixtures were archived directly. The final documentation rebuild was byte-identical to the validated runtime.

Tested in the isolated test vault and ready for the user's BRAT pull. Production remains untouched; device acceptance is separate.
