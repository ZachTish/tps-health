# TPS Health 3.8.7 — Food indexing follows provider readiness

Backward-compatible patch for macros and food history showing zero after plugin startup. Minimum Obsidian: **1.12.0**. Tested in the isolated test vault and ready for the user's BRAT pull; not installed in production by this release workflow.

## Cause and fix

Health could complete its metadata index before GCM's asynchronous native-record API became available. All notes were skipped, and later metadata-resolution events intentionally avoided repeating a settled scan. Health did not consume GCM's existing API-readiness announcement, leaving valid records invisible until a separate index refresh.

Health now listens to `tps:gcm-api-changed`, waits for a usable API v6 provider before declaring the index settled, and indexes cached metadata when that provider is ready. Already-open macros/day consumers receive their existing record-change notifications.

Reloads retain accepted records during provider unavailability, invalidate pre-reload pending reads, and reconcile edits/removals on return. Previous dates receive change notifications as well as current dates. Unchanged provider announcements do not rescan: provider identity and exposed global/per-kind classification profiles determine whether reconciliation is needed. Deferred legacy workout hydration waits for both metadata and provider readiness, avoiding duplicate startup body reads.

No persistent settings, schemas, API versions, migrations, polling, automatic repair, or new note-writing route. Existing food notes do not need to be re-entered. No changes to TishOS widgets, Relay, nutrient calculations, or other plugins.

## Validation

- Full declared `npm test`: **560 passed, 0 failed, 1 skipped** (optional live USDA credential-dependent check). Includes nine new lifecycle tests and 97 native-record tests.
- TypeScript and the mandatory separate `npm run build` pass. Deployment targets only the isolated test vault; the separate build was byte-identical.
- The installed-service comparison executes the shipped Health service and real GCM classifier with synthetic in-memory files and controlled provider timing. On 3.8.6, a 210 kcal entry stays at zero after readiness; on 3.8.7 it becomes 210 kcal. Fixed run: one metadata pass, one change notification, zero raw/cached body reads or writes; 100 repeated unchanged lifecycle/navigation bursts add none. These scoped counts are not whole-app disk-I/O measurements.
- Actual installed lifecycle: temporarily disable test-vault GCM, load Health, then enable GCM. The open Live Preview macros block changed from 0 to 210 kcal / 12 g protein / 27 g carbs / 6 g fat without editing or reopening the note. The final versioned bundle repeated that lifecycle with one rebuild, correct totals and a settled index. The real provider was present in Obsidian's registry at its readiness event.
- Existing consumer plugins remained enabled; only Health and GCM were temporarily reloaded for their lifecycle test. No outbound provider/import automation was enabled. Obsidian Sync remained disabled. Health, GCM, Controller, Calendar and Finances settings were byte-identical before and after QA. Synthetic fixtures were archived; no production records/settings were modified.
- Unit coverage includes three provider/metadata/layout orderings, provider replacement, missed removals, classification changes including tag mappings, unchanged announcements, disposal, stale read invalidation and single-pass workout hydration.

No physical-phone startup or production-performance claim. Unavailable/disabled GCM still cannot classify records; the fix responds when the supported provider becomes available rather than adding retries or a second classifier.
