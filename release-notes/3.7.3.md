# TPS Health 3.7.3

Ordinary note creation, editing and renaming no longer cause Health to reread every changed Markdown file. This removes unrelated file-queue work and prevents ordinary edits from temporarily disabling workout controls.

## Changes

- Obsidian's metadata `changed` event owns discovery of external Health records and supplies both the frontmatter and legacy workout body source. No competing generic create reader remains.
- Health-owned create/edit operations still update their index immediately from the returned record. Already-known Health sources and the saved active-workout path retain scoped refreshes and the existing pending-workout guard; read-only hydration uses `cachedRead` rather than raw reads. A newly arrived active-workout file remains protected until its source is available.
- Known Health renames still refresh, because Obsidian intentionally does not emit metadata `changed` for a rename.
- Missing or invalid indexed frontmatter removes the previous identity rather than recovering it from stale metadata. This changes only in-memory display/index state; no repair or migration rewrites notes.
- An indexed source invalidates any older pending read. Unique tokens in the existing pending-read map prevent an old result from overwriting newer workout data or releasing a later edit guard. Rename and delete invalidate the prior path token so an obsolete read cannot leave workout controls waiting indefinitely.

Patch release: no settings, storage schema, public API or minimum-version changes. Requires Obsidian **1.12.0+**.

## Validation

The three initial regression cases failed on 3.7.2. The revised focused suite passes 74 native-record checks, including 128 ordinary create/edit/rename sequences with **zero raw reads, cached reads, vault scans or write attempts** by the Health index. Coverage includes external creation and ordinary-to-Health classification, body-only legacy workout changes, invalid YAML and removed identity, known-record edits before metadata catches up, rename without metadata notification, rename/delete during pending reads, out-of-order reads, metadata overtaking an older read, cancellation followed by another edit, an active-workout file arriving before metadata, startup hydration and disposed services.

The final versioned declared suite passed **504 tests, zero failures, one optional live USDA check skipped without a credential**, including TypeScript. The stable build deployed to the isolated test vault; a named disable/load-manifest/enable reload verified 3.7.3. The separate normal final build after documentation confirms the same validated runtime artifacts.

Installed QA used the same synthetic Inbox workload on 3.7.2 and 3.7.3, attributing reads only inside Health refreshes for those fixture paths:

| Workload | Version | Health refreshes | Direct Health `Vault.read` | Health `cachedRead` | Core cache-fill `Vault.read` |
| --- | --- | ---: | ---: | ---: | ---: |
| Three ordinary create/edit/rename sequences | 3.7.2 | 9 | 9 | 0 | 0 |
| Same ordinary actions | 3.7.3 | 0 | 0 | 0 | 0 |
| Workout discovery, set edit, rename | 3.7.2 | 3 | 3 | 0 | 0 |
| Same workout actions | 3.7.3 | 2 | 0 | 2 | 1 |

Both versions discovered the external workout, showed the edited set changing from 5 to 12 reps, settled the renamed record's index, and preserved its body and Health/GCM settings. The initial new-version probe failed an overly strict zero-nested-read assertion. That failure was preserved; a corrected repeat captured the stack proving the one read originated inside core Obsidian's `cachedRead` cache-fill path, with zero direct raw reads by Health. Calling `cachedRead` is not a guarantee of zero physical I/O. No timing improvement percentage is claimed.

## Limits

An unknown external note becomes available to Health when Obsidian emits its metadata indexing event. An immediate action before that event cannot assume the note has been discovered; this matches the metadata-owned read model. Health-owned creation/editing remains immediately indexed. Known-record refresh safeguards and authoritative mutation checks remain in place.

This change does not remove every Health observer or claim a production timing percentage. Settings/connection surfaces and physical iPhone behavior are unchanged; no live provider or outbound automation is required for validation. Production is not modified; this release is tested in the test vault and ready for the user's BRAT pull. It is not evidence of installation or acceptance in production.
