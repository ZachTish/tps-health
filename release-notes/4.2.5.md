# TPS Health 4.2.5

Backward-compatible startup/discovery performance correction; minimum Obsidian 1.12.0.

## Change and ownership

Initial and configuration/provider-triggered Health native-record discovery now yields between batches targeting 8 ms or at most 256 path operations. An explicitly cold metadata cache takes one current inventory at first resolution instead of scanning at both setup and resolution. Warm loads, including mobile hosts without the private initialized flag, still use public cache coverage. Existing incremental handlers own ordinary metadata/body edits, create, delete and rename; settled resolution events perform no inventory or indexing work.

The only added state is a transient discovery owner and its completion promise. It carries current path work across real task boundaries; it is not a second persisted index. Native scheduler.yield is feature-detected. Older browser hosts use a one-shot MessageChannel and close both ports. The compatibility timer is used only when neither browser facility exists. This avoids a measured hidden-window timer-queue delay, not operating-system suspension: iOS may suspend Obsidian regardless of task primitive.

Accepted data retains its loading/partial status during discovery. Unavailable metadata preserves accepted records; current identity and newer source events prevent a queued cache from overwriting current files. Pending metadata resolution requests are coalesced and drained, including requests received during a catch-up. Provider/configuration replacement and disposal invalidate earlier work, and errors settle the owning promise without an automatic retry.

The existing asynchronous daily-macro API and deferred food projection wait for the current full pass. Workout session mutations wait at the central boundary, then retain current-source and atomic conflict checks. This does not cancel an already-entered GCM atomic write. Pending-only catch-up retains known workout write availability. Legacy body hydration remains scoped to sessions without the modern nested session property, and an earlier layout callback does not start duplicate hydration during a newer full pass.

No setting, record format, public API shape, cache, poller, watcher, migration or automatic repair is added. RefreshConfiguration keeps its existing void contract; displays may show accepted provisional data while a full pass completes.

## Regression evidence

Twenty-three new actual-service tests cover cold single-inventory startup, warm/missed resolution, operation/time batch boundaries, every task-yield branch and closed ports, edits with stale cache, current file identity, create/delete/rename/replacement, unavailable metadata, resolution bursts during catch-up, configuration/provider replacement, disposal, async API and deferred projection waits, legacy hydration ownership, and workout mutation races at resolve/read/atomic boundaries. Failure cases cover inspection exceptions, scheduler rejection and completion callback exceptions with settled waiters and the proven ready-status notification.

All 161 native-record checks pass and independent source/test review found no blocking lifecycle/readiness/data-safety issue. The full declared versioned suite passed 640 of 641 checks under Node 24.19.0, with zero failures/cancellations; the existing optional USDA check skipped without its test API key. The unauthenticated public Open Food Facts barcode check passed. TypeScript and the test build passed with TPS_NO_DEPLOY=1. No configured importer/provider automation was enabled and no personal data was sent.

## Composed replay and limits

An isolated in-memory harness composes the actual Health service with actual GCM 7.3.11 public inspection across 11,121 synthetic Markdown files: 10,000 ordinary notes, 1,000 linked food entries, one food definition, 100 activity records, and ten modern plus ten legacy workouts. A newly discovered startup food makes the cold inventory 11,122 files. Thirty configured kinds stress the mapped path; these are synthetic mappings, not the installed Test-vault configuration. Raw I/O and mutating calls reject; source bytes remain unchanged.

In the mapped cold case, Health setup performs no inventory or indexing. First resolution performs one inventory and 11,122 inspections, with 66 measured task slices and a longest 8.848 ms slice; total completion is 534.31 ms. Warm mapped setup completes in 74 slices with a longest 9.158 ms slice. Twenty settled resolution deliveries perform zero inventories/inspections. Both formats retain their sets; modern sessions take zero cached body reads and ten legacy sessions take ten existing scoped cached reads. There are zero raw reads, persistence schedules or mutation attempts. Partial warm discovery retains 301 unknown paths, then catches those paths up without another inventory.

These harness timings are not foreground UI or physical-device timings. GCM's separate mapped startup remains a synchronous approximately one-second task in this stress case and is not changed here. A single file's inspection and existing subscriber fan-out cannot be preempted, so the batch target is not a hard 8 ms bound. The patch removes Health's duplicated cold scan and yields between its necessary discovery work; it does not claim to resolve every source of the user's multi-second mobile/Windows freezing.

## Installed validation and handoff

The mandatory separate ordinary production-mode build deployed only changed main.js and manifest.json to Obsidian Plugin Test Vault. An exact CLI vault/path guard preceded deployment. A Health-only manifest refresh and reload confirmed installed 4.2.5, with the same 182 accepted records before and after, no raw reads or writes, and 14 existing legacy cached body reads. Health data.json stayed byte-identical at 6484ad66a8d3981cca16a0d423ff13e41a8a5fa988215aafdd37a54d2368d281, with saved settings/state and the absent active workout unchanged. Instrumented methods were restored.

The same actual warm reload comparison ran in hidden, unfocused Electron 30.1.2/Chromium 124 with enabled consumers. The earlier 4.2.4 longest Node-heartbeat reload gap was 184.2 ms (idle 20.5 ms, settled 21.6 ms); 4.2.5 was 29.6 ms (idle 20.2 ms, settled 20.3 ms). Plugin reload returned at 70 ms with an honestly partial index, then reached ready at 233.7 ms, versus 230.2 ms ready/return on 4.2.4. This is a blocking-slice improvement, not faster total discovery. Health inventories remained one; metadata lookups changed from 15,411 to 15,834 because the new contained source worktree added Test-vault Markdown files between runs. Both versions made the same 14 legacy cached reads.

Combined installed Live Preview QA with Health 4.2.5, GCM 7.3.11 and Navigator 8.2.3 passed 13 phases, including three first mounts, six tab switches, two remounts and idle controls. Observed Macros/Activity surfaces retained 24 food rows and 39 workout/activity rows for the selected saved dates, with no render/phase errors, captured long tasks or navigation note-mutation attempts. Three UUID Inbox fixtures kept their exact bodies and moved directly to _archive; the original leaf, methods, observers, saved settings/data and absent active workout were preserved. Background workspace-state writes were counted separately from note writes.

The installed comparison is warm Health-only reload and hidden/unfocused Live Preview navigation, not cold process startup, physical input or mobile/Windows timing. Daily QA uses explicit date filters; implicit mapped Daily Note recognition, Reading mode, disclosure expansion, real food/activity edits, provider actions and active-workout interactions are outside that installed flow. Physical iPhone/iPad/Windows responsiveness remains unverified. The final post-documentation ordinary build is byte-identical to the compared artifacts and leaves the Test-vault data unchanged.

Test-vault validation is complete. This release is prepared for the user's BRAT pull; no direct production installation is included.
